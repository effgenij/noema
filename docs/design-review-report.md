# Adversarial Review — Iteration 2
**Doc:** effgenij-cortex-design-20260907-201842.md (Cortex, этап 1 lifeOS)
**Дата:** 2026-09-07 · **Оценка: 8.5/10**

## Общий вердикт
Проблема итерации 1 (механизм обновления UI при записи агентом) **исправлена** — раздел Recommended Approach теперь явно описывает host.onEvent + polling-fallback + локальную перерисовку ручных правок (строка 71). Документ зрелый: ограничения проверены по исходникам платформы, скоуп зажат, критерии успеха проверяемы. Остались точечные замечания, ни одно не блокирует начало T1.

## По измерениям

### 1. Completeness — PASS (с 1 заметкой)
- Все ключевые механизмы описаны: БД (plugin_db WAL), REST (ctx.rest → /api/plugins/cortex/), UI (страницы/сайдбар), агентные инструменты, обновление UI, бэкап, переносимость.
- Заметка (не блокер): не указано, **чем именно** Python-инструмент эмитит событие гейтвея для host.onEvent. Контекст платформы подтверждает, что события гейтвея существуют, но API эмиссии изнутри `ctx.register_tool`-инструмента в доке не назван.
  **Fix:** в T2 добавить шаг «верифицировать API эмитирования события из Python-инструмента»; polling-fallback (3с) уже гарантирует работоспособность, если API не найдётся — риск сведён к задержке обновления.

### 2. Consistency — 2 незначительные проблемы
- **Противоречие о месте кода.** Строка 4: «repo пустой — код будет жить в ~/.hermes/plugins/», а Distribution Plan: «git-репо хранит исходники, деплой = копия/симлинк в ~/.hermes/plugins/».
  **Fix:** переформулировать строку 4: «исходники в ~/dev/personal/cortex, деплой симлинком/копией в ~/.hermes/plugins/».
- **Критерий 6 зависит от нерешённого OQ2.** Success Criteria №6 строится на `data-hermes-send`, а Open Question 2 («data-hermes-send vs ctx.rest из preview-iframe») ещё открыт.
  **Fix:** пометить критерий 6 как зависящий от дефолта OQ2 (промпт агенту) или явно закрыть OQ2 дефолтом до старта T5.
- Остальное сходится: ::preview ≤500 симв. и отказ от chart-библиотек заявлены в Constraints и соответствуют SDK; гибрид данных (P6) и стартовые модули (P7) совпадают с Recommended Approach и Next Steps.

### 3. Clarity — PASS
- Механизм обновления UI изложен однозначно: событие → инвалидация кэша → перерисовка; fallback-опрос 3с; локальная перерисовка при ручных правках.
- Терминология (ROUTES_AREA, SIDEBAR_NAV_AREA) — внутренний жаргон исследования, но для целевого читателя (сам автор) приемлема. Замечание не требуется.

### 4. Scope — PASS
- v1 жёстко ограничен: tasks/notes/habits + ядро + хоум; learning/body/money/feed вынесены в этап 2 (T7). Дженерик-движок явно исключён (P4).
- Чат не дублируется — ограничение платформы превращено в осознанное решение.
- Расширяемость не лозунг, а проверяемый критерий №8. Скоуп сбалансирован.

### 5. Feasibility — PASS (с 1 заметкой)
- Все заявленные возможности подтверждены по исходникам: ctx.register_tool, FastAPI-бэкенд, plugin.js без JSX/chart-библиотек, host.onEvent, ctx.rest, ::preview + window.hermes.send, plugin_db (WAL), hot-reload.
- SVG-графики собственными компонентами — реалистично для спарклайнов стриков.
- WAL покрывает конкурентный доступ FastAPI-бэкенда и агентных инструментов к одной базе.
- Заметка: эмиссия события из Python-инструмента — единственное неподтверждённое звено цепочки «запись агентом → перерисовка» (см. Completeness). Fallback-поллинг делает риск некритичным.
