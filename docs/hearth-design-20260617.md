## Pivot summary

**Before:** Two-process architecture. `hearth-app` (Tauri UI) + `hearth-mcp` (separate Rust binary) sharing a SQLite file. Cross-process coordination via SQLite WAL + persisted lamport counter. Hermes Agent talked to `hearth-mcp` over stdio JSON-RPC from a separate Hermes GUI.

**After:** Single-process Tauri app. One Cargo crate, one binary, one Tauri window. Three zones inside the window:
- **Left sidebar:** Hermes chat (streaming, tool-calls, markdown)
- **Right panel:** tabbed tree of domains/projects (like Notion — top-level domains, subfolders, custom user pages)
- **Center canvas:** the active tab's layout, with draggable widgets that show data and into which the agent can output data

**Why the pivot:** During `/plan-eng-review`, the user clarified the actual UX shape verbally. The original plan described "Notion for life with an external agent"; the user's mental model is "single Tauri window with three zones, where the agent lives in the left sidebar and writes to widgets in the center canvas." This is a hybrid of `fathah/hermes-desktop` (chat UI) and `pewdiepie-archdaemon/odysseus` (project/tab layout), not a Notion-clone + external-agent architecture.

**What this removes:**
- Separate `hearth-mcp` binary (MCP server is embedded in the Tauri app)
- Cross-process coordination (SQLite write-lock from BEGIN IMMEDIATE, persisted lamport counter for cross-process uniqueness)
- Migration race-avoidance (single process owns the DB; no contention)
- Backup-portability of the keychain (same complexity, but now single-process to reason about)

**What this keeps:**
- Local-first, encrypted at rest, no VPS in v1
- Data layer with event log (still useful for future VPS-sync, even from a single process)
- 5 MCP tools, all the same, just exposed in-process instead of over stdio
- Bidirectional UI↔agent control with pinning
- 6 first-queue domains, 5 block types

## Problem Statement

The user has six life domains they want to operate on with an AI agent: finance, health, fitness, tasks, email, habits. Today, talking to the agent is a separate app from looking at the data, so they end up scrolling back through chat logs to remember "wait, what was my average spend last week?" — even when the agent just edited that record two minutes ago. They want one window where the chat is on the left, the data is in the center, and both can edit the same widgets without either silently breaking the other.

## What Makes This Cool

The "whoa" is **a single working surface where the agent and the data are co-tenants of the same window**. You switch to the Finance tab on the right, ask Hermes in the left sidebar "what did I spend on coffee last week?", and a chart pops into the center canvas. You drag a row to pin it. You create a new "Q3 fitness" subfolder, drop a "weekly weigh-in" widget into it, and tell Hermes "log today's weight" — the widget updates in place. No app switching, no copy-paste between tools, no "wait which app was that in."

The second "whoa" is **the agent is always in the same process as the data it acts on**. No HTTP round-trips, no MCP stdio, no subprocess. The agent's tool calls are direct function calls into the same Rust code that the UI uses. Latency drops from ~50ms (MCP stdio) to ~1ms. The cost of an agent action is invisible to the user.

The third "whoa" is **layout-as-data, not layout-as-document**. Notion treats each page as a document. Here, the layout is a first-class data structure the agent reasons about and edits programmatically. The agent can answer "where is my March weight chart?" by querying the layout-store, not by parsing a doc.

## Constraints

- **Personal tool, not a startup.** No users besides the builder. No monetization. No growth. (Premise P1.)
- **Local-first MVP.** No VPS, no cloud, no cross-device sync in v1. Data lives on the mac. (Premise P4.)
- **Single Tauri process.** The Tauri app, the embedded MCP server, and the Hermes chat runtime are all one binary. The agent talks to the data layer via direct Rust function calls, not IPC. Cross-process coordination is deferred to whenever a second-process use case appears (e.g., external MCP client).
- **VPS-sync later is a hard requirement of the design**, not an afterthought. The data layer must be shaped so adding a remote replica is a transport adapter, not a rewrite. This still drives UUIDv7 identifiers and an append-only event log with a persisted lamport counter — both still useful even single-process, because they enable future sync without changing the v1 schema. **Future transport boundary (sketch, not implemented):** a `SyncTransport` Rust trait with `push(events: &[EventLogRow]) -> Result<()>` and `pull(since_lamport: i64) -> Result<Vec<EventLogRow>>`. Implementations over Tailscale+WebSocket, libp2p, etc. The data layer's only contract with the transport is the trait; everything else (merge logic, conflict resolution) lives above the trait and is transport-agnostic.
- **The six domains already have decent solutions** (Apple Health, banking apps, Mail.app, Reminders). The value isn't replacing those; it's giving the agent a structured view across them and giving the user one working surface.
- **The builder already uses Hermes** on macOS — embedding the Hermes Agent runtime (the open-source one, not the GUI) is the path of least resistance.
- **The builder is opinionated about taste** — wants no WYSIWYG bloat, prefers deliberate pinning over implicit safety, wants the agent to be a peer editor, not a primary actor.

## Data Layer Decisions

These are still locked by the VPS-future requirement, but **simpler than the prior design** because the single-process model removes the cross-process concerns.

### Identifiers

- Every row uses **UUIDv7** (sortable by creation time, globally unique, no collision across replicas).
- Foreign keys reference UUIDv7s.
- SQLite `PRAGMA foreign_keys = ON;` enforced.

### Lamport counter (persisted, for future sync — not for v1 race avoidance)

In a single-process app, an in-memory counter is fine. We **still persist it** in `meta.lamport_counter` because the moment a second process joins (remote agent, mobile app, VPS replicator), we need a globally monotonic ordering. The cost is one extra `UPDATE meta` per mutation, which is negligible at personal scale (<100 mutations/sec).

### Event log retention (v1)

v1: append-only, **manual compaction only**. Settings → Database → "Compact event log" button snapshots the current state of all tables into a new SQLite file, deletes the old `event_log` rows older than 90 days (configurable), and `VACUUM`s the file. This is a one-shot operation; not automated. Post-MVP: snapshot-and-prune on a schedule (cron-style).

### SQLite schema (DDL for v1)

```sql
-- meta: singletons (lamport counter, schema version)
CREATE TABLE meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);

-- workspaces: top-level container; v1 = single default workspace per user
CREATE TABLE workspaces (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL,
  created_at TEXT NOT NULL
);

-- pages: tabs in the right panel. Hierarchy via parent_id (one level of nesting for v1, recursive CTE ready for v2)
CREATE TABLE pages (
  id          TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  parent_id   TEXT REFERENCES pages(id) ON DELETE CASCADE,  -- null = top-level; v1 limits to 1 level of nesting
  title       TEXT NOT NULL,
  icon        TEXT,
  ordinal     INTEGER NOT NULL,                            -- order among siblings
  page_type   TEXT NOT NULL CHECK (page_type IN ('domain','custom')),
  domain_slug TEXT,                                        -- 'finance' | 'health' | etc; null for custom pages
  created_at  TEXT NOT NULL,
  deleted_at  TEXT                                         -- soft-delete
);
CREATE INDEX idx_pages_parent ON pages(parent_id, ordinal) WHERE deleted_at IS NULL;
CREATE INDEX idx_pages_workspace ON pages(workspace_id) WHERE deleted_at IS NULL;

-- layouts: one per page (1:1)
CREATE TABLE layouts (
  id         TEXT PRIMARY KEY,
  page_id    TEXT NOT NULL UNIQUE REFERENCES pages(id) ON DELETE CASCADE,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- blocks: individual widgets in a layout
CREATE TABLE blocks (
  id           TEXT PRIMARY KEY,
  layout_id    TEXT NOT NULL REFERENCES layouts(id) ON DELETE CASCADE,
  block_type   TEXT NOT NULL,    -- 'table' | 'counter' | 'list' | 'note' | 'chart'
  config       JSON NOT NULL,    -- block-type-specific config
  ordinal      INTEGER NOT NULL,
  title        TEXT,
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);
CREATE INDEX idx_blocks_layout ON blocks(layout_id, ordinal);

-- records: data rows belonging to a block
CREATE TABLE records (
  id          TEXT PRIMARY KEY,
  block_id    TEXT NOT NULL REFERENCES blocks(id) ON DELETE CASCADE,
  fields      JSON NOT NULL,
  amount      REAL,             -- finance convenience column; null otherwise
  currency    TEXT,             -- ISO 4217; null if not monetary
  occurred_at TEXT NOT NULL,    -- ISO 8601 UTC
  tz          TEXT,             -- IANA timezone at occurrence
  created_at  TEXT NOT NULL
);
CREATE INDEX idx_records_block_time ON records(block_id, occurred_at DESC);

-- pins: a pinned block cannot be edited/deleted/reordered or have records added to it
CREATE TABLE pins (
  block_id  TEXT PRIMARY KEY REFERENCES blocks(id) ON DELETE CASCADE,
  pinned_at TEXT NOT NULL,
  pinned_by TEXT NOT NULL CHECK (pinned_by = 'user')  -- user-only; agent pin is rejected before reaching SQL
);

-- proposals: agent-suggested blocks
CREATE TABLE proposals (
  id          TEXT PRIMARY KEY,
  page_id     TEXT NOT NULL REFERENCES pages(id) ON DELETE CASCADE,
  block_type  TEXT NOT NULL,
  config      JSON NOT NULL,
  rationale   TEXT NOT NULL,
  status      TEXT NOT NULL CHECK (status IN ('proposed','accepted','rejected','expired','superseded')),
  created_at  TEXT NOT NULL,
  expires_at  TEXT NOT NULL,
  decided_at  TEXT,
  decided_by  TEXT CHECK (decided_by IN ('user','auto-expire'))
);
CREATE INDEX idx_proposals_status_expires ON proposals(status, expires_at);

-- event_log: every mutation recorded. prev_hash is a SHA-256 chain link for tamper detection (audit only, not used for merge).
CREATE TABLE event_log (
  id          TEXT PRIMARY KEY,
  record_id   TEXT NOT NULL,
  table_name  TEXT NOT NULL,
  op_type     TEXT NOT NULL CHECK (op_type IN ('create','update','delete')),
  payload     JSON NOT NULL,
  prev_hash   TEXT,                -- null for genesis event; SHA-256 of previous event_log row for this record_id
  lamport_ts  INTEGER NOT NULL,
  agent_id    TEXT NOT NULL CHECK (agent_id IN ('user','hermes')),
  created_at  TEXT NOT NULL
);
CREATE INDEX idx_event_log_record ON event_log(record_id, lamport_ts);
CREATE INDEX idx_event_log_time ON event_log(created_at DESC);
CREATE INDEX idx_event_log_lamport ON event_log(lamport_ts);
```

### `event_log.payload` shape

- `create`: `{"after": {<full new row as JSON object excluding id>}}`
- `update`: `{"after": {<changed fields only, partial — only what the caller passed to applyMutation>}}` — partial so LWW-per-field merge can pick winners per field
- `delete`: `{"id": "<uuidv7>", "before_summary": {<row snapshot>}}`

A future VPS-sync replicator does LWW-per-field merge by comparing field values from events with higher `(lamport_ts, agent_id)` lexicographic order.

### Encryption-at-rest

SQLCipher with a 32-byte key. Key lifecycle:

1. **First launch:** `SecRandomCopyBytes` → 32 random bytes → keychain via `security add-generic-password -s hermes-workspace.db -a sqlcipher-key -w <key>` → `PRAGMA key`. macOS shows a one-time "Hermes Workspace wants to access the Keychain" prompt. The Onboarding screen guides the user: "macOS will ask permission to store your database encryption key in the Keychain. Click 'Always Allow' to keep Hearth working without re-prompting on every launch." If the user denies: Hearth shows a blocking modal — "Keychain access denied. Hearth cannot function without storing the encryption key. Open System Settings → Privacy & Security → Keychain Access and grant permission to 'Hermes Workspace', then restart Hearth." There is no in-app retry; denial is a one-way door until the user changes OS settings.
2. **Subsequent launches:** read key from keychain → `PRAGMA key`. If keychain read fails → fail fast with a clear error.
3. **Backup:** a "Backup now" button in Settings produces a `.tar.gz` containing `hermes-workspace.db`. **The SQLCipher key is NOT included** — the user supplies a passphrase at backup time, and the archive is encrypted with `age` (https://age-encryption.org) using a recipient derived from the passphrase. The recipient is shown to the user as a "passphrase hint" string so they can recover it from memory or a password manager.
4. **Restore:** user picks the `.tar.gz` in Settings → Restore, supplies the passphrase, Hearth decrypts, extracts `hermes-workspace.db`, opens with the keychain-resident key. **Round-trip integrity required.**
5. The env var `HERMES_WORKSPACE_DB_PATH` lets power users point Hearth at an alternate DB location (e.g., testing); the UI also exposes this in Settings → Database path.

UI documents prominently: **"Losing the key OR the passphrase = losing the data. Keep both safe and separate."**

**Backup passphrase hint:** when the user creates a backup, Hearth shows them a hint consisting of (a) the age recipient fingerprint — first 16 chars of `age-keygen`'s recipient string (e.g., `age1qwertyuiopasdf`) — and (b) the backup timestamp (ISO 8601 UTC). The user stores the hint alongside their passphrase (in a password manager, or written down). On restore, if the user forgets the passphrase but has the hint + recipient fingerprint, they can attempt recovery by brute-forcing against the hint — but the fingerprint is for record-keeping, not recovery magic.

### Migrations

- `PRAGMA user_version` holds the schema version.
- Migration SQL files in `src-tauri/migrations/v001_initial.sql`, etc., wrapped in `BEGIN; ... COMMIT;`.
- On launch, read `user_version`, run unapplied migrations in order, bump `user_version`.
- Drizzle-kit is used for **schema→TypeScript-type generation only** (e.g., `drizzle-kit generate` produces a `.d.ts` file matching the schema). It is **not** a runtime DB driver — actual DB I/O flows through Tauri commands. SQL migrations are authoritative; when you change schema, write migration SQL by hand, then update the Drizzle TS to match.

### SQLite client (custom, not tauri-plugin-sql)

**`tauri-plugin-sql` does NOT work with SQLCipher** — it ships against plain `rusqlite`, and the SQLCipher feature is a fork. Therefore Hearth uses a **custom Tauri command path** for SQL:

- Rust code calls `rusqlite::Connection::open(path)` → `PRAGMA key = '...'` → use directly.
- A `db_pool` module in `hearth-core` owns the single `Connection` (single-process app, no contention).
- All Tauri commands for DB access are defined in `hearth-core::commands` and exposed to the webview via `#[tauri::command]` macro.
- `drizzle-kit` is used for typed JS reads from the TypeScript side; SQL migrations are authoritative.

This deviates from the prior design's "use `tauri-plugin-sql`" recommendation. Trade-off: ~50 lines of custom Tauri command boilerplate vs. shipping without encryption. Encryption wins.

## Architecture (single process)

```
hermes-workspace (one Tauri binary)
├── Tauri webview (React + TypeScript UI)
│   ├── Left sidebar: ChatPanel (Hermes chat UI — streaming, markdown, tool-call display)
│   ├── Right panel: PageTree (tabbed tree of pages/domains)
│   └── Center canvas: LayoutCanvas (draggable widgets)
│
├── Rust backend (single process, single Cargo crate)
│   ├── Tauri commands (UI ↔ backend bridge)
│   ├── hearth-core module
│   │   ├── applyMutation(m: Mutation, agent_id: &str) → Result<MutationResult, MutationError>
│   │   ├── PageTree API (read + write pages)
│   │   ├── Layout API (read + write layouts/blocks/records)
│   │   ├── Pin API
│   │   ├── Proposal API + auto-expire sweeper (tokio interval, hourly)
│   │   └── Backup API (age-encrypted .tar.gz, no key inside)
│   ├── Embedded MCP server (listens on localhost:<port>, default OFF in v1 — gated by Settings)
│   └── Hermes Agent subprocess (Node.js child process, stdio JSON-RPC, lifecycle owned by Tauri)
```

### `applyMutation` signature (locked)

```rust
pub enum Mutation {
    CreateWorkspace { name: String },
    CreatePage { workspace_id: Uuid, parent_id: Option<Uuid>, title: String, icon: Option<String>, page_type: PageType, domain_slug: Option<String> },
    UpdatePage { id: Uuid, fields: serde_json::Value },
    DeletePage { id: Uuid },  // soft-delete
    CreateBlock { layout_id: Uuid, block_type: BlockType, config: serde_json::Value, title: Option<String>, ordinal: i32 },
    UpdateBlock { id: Uuid, fields: serde_json::Value },  // partial; only changed fields
    ReorderBlocks { layout_id: Uuid, new_ordering: Vec<Uuid> },
    DeleteBlock { id: Uuid },
    PinBlock { id: Uuid },       // rejected with PIN_NOT_ALLOWED if agent_id != 'user'
    UnpinBlock { id: Uuid },     // rejected with PIN_NOT_ALLOWED if agent_id != 'user'
    AddRecord { block_id: Uuid, fields: serde_json::Value, amount: Option<f64>, currency: Option<String>, occurred_at: DateTime<Utc>, tz: Option<String> },
    CreateProposal { page_id: Uuid, block_type: BlockType, config: serde_json::Value, rationale: String },
    AcceptProposal { id: Uuid },
    RejectProposal { id: Uuid },
    ExpireProposal { id: Uuid },
}

pub enum BlockType { Table, Counter, List, Note, Chart }
pub enum PageType { Domain, Custom }

pub enum MutationResult {
    Created(Uuid),   // new row's id
    Updated,
    Deleted,
    NoOp,
}

pub enum MutationError {
    NotFound,
    BlockPinned,
    PinNotAllowed,
    ValidationFailed(String),
    DbError(String),
}

pub fn applyMutation(m: Mutation, agent_id: &str) -> Result<MutationResult, MutationError>;
```

`agent_id` is passed in (not read from the mutation) so the function can enforce user-only invariants for `PinBlock`/`UnpinBlock`.

**Transaction isolation:** `applyMutation` runs inside a `BEGIN IMMEDIATE` transaction (acquires SQLite's write lock at the start). The transaction bundles: (1) lamport counter bump, (2) event_log row insert, (3) target table mutation. All three commit atomically. If any step fails, the whole transaction rolls back — partial state is impossible. Even in a single-process app this matters because the Tauri command handler and the in-process broadcast channel can be invoked concurrently from different UI events; `BEGIN IMMEDIATE` serializes them through SQLite's lock.

### Block type configs (locked)

Each block type has a `config: JSON` field with a Zod-validated shape. Schema per type:

```typescript

TableConfig = {

// Per-domain column presets: finance → [amount, currency, category, note, occurred_at]

// Default record fields: { value: number }

// List: title + optional body + checkbox

}

// Note: single rich-text field

}

```

### Hermes Agent subprocess wire format (provisionally locked — depends on Open Q1)

The Tauri Rust backend spawns `hermes-agent` as a child process on app launch. Communication is stdio JSON-RPC 2.0. **Hearth is the MCP server; the Hermes Agent subprocess is the MCP client.** The 5 `hearth.*` tools are exposed by `hearth-core::mcp` and consumed by Hermes over stdio. Chat tokens flow from Hermes stdout → Tauri → webview; tool calls flow from Hermes stdin → Tauri command handler → `applyMutation` → result returned to Hermes on stdout.

**This depends on Open Question #1** — the open-source Hermes Agent must expose an MCP-client mode that connects to a server over stdio JSON-RPC. The v1 wire format is provisionally locked; if Hermes Agent doesn't support this, we fall back to spawning it with `--print` mode and parsing stdout (degraded but feasible).

**Lifecycle:**
- App launch: spawn `hermes-agent --mcp-client-config ~/.hermes-workspace/mcp.json` (exact flag TBD per Open Q1)
- Hearth registers its 5 `hearth.*` tools with Hermes via MCP `initialize` + `tools/list` handshake
- User types in ChatPanel → Tauri command → write JSON-RPC request to Hermes stdin → Hermes invokes hearth.* tool → result streams back via stdout → Tauri emits `data-changed` event → UI re-renders
- App quit: SIGTERM the subprocess, wait up to 2s, then SIGKILL

**Wire format (JSON-RPC 2.0 over stdio):**
- `initialize` / `initialized` handshake on startup
- `tools/list` → Hearth returns the 5 hearth.* tools
- `tools/call` → Hermes calls a hearth.* tool → Hearth invokes `applyMutation` → returns `MutationResult`
- `notifications/message` → Hermes streams chat tokens back to the UI via `app_handle.emit("chat-token", ...)`

### Chat panel architecture

The chat panel in the left sidebar is the only place where the user interacts with Hermes. It's **embedded in the Tauri webview**, not a separate app. Stream events from Hermes flow into the React chat component via a Tauri event channel (`app_handle.emit("chat-token", ...)`).

Tool calls from Hermes flow the other way: Hermes invokes a hearth.* tool → Hearth (in-process) calls `applyMutation` → result returned to Hermes over stdout → UI re-renders via Tauri event. Latency: **<10ms end-to-end, in-process chat only** (external MCP clients experience ~1s polling latency; see "Update propagation paths" below).

## MCP Server (embedded, gated)

The MCP server is **a module inside the Tauri app**. It listens on `127.0.0.1:<port>` (port chosen at launch, exposed in Settings) and serves 5 tools over JSON-RPC. **In v1, it is OFF by default** — Settings → "Enable external MCP server" toggles it on. When ON, Hearth generates a bearer token (256-bit random, shown once in Settings) that external MCP clients must send as `Authorization: Bearer <token>`. The token is stored in keychain, not the SQLite DB.

**Why OFF by default:** the v1 chat panel uses the Hermes subprocess directly via in-process function calls. The embedded MCP server exists only for external clients (Claude Code, Codex, etc.). For a personal tool, exposing it is a security regression unless explicitly enabled.

**Role separation (clarified):**
- `hearth-core::mcp` is the **server** exposing the 5 `hearth.*` tools, consumed by two distinct clients:
  - **In-process chat:** the Hermes Agent subprocess connects to it over stdio JSON-RPC. Latency <10ms.
  - **External clients:** Claude Code / Codex / etc. connect to it over HTTP+bearer at `127.0.0.1:<port>`. Latency ~1s (polling fallback).
- The Tauri → webview direction is for chat tokens and data-changed events, not for tool calls.

### Tool schemas (v1)

```json
hearth.add_record
  input: {
    page_id: string (UUIDv7),
    block_id: string (UUIDv7),
    fields: object (block-type-specific; e.g. {amount: number, currency: string, category: string, note: string} for finance)
  }
  success: {record_id: string (UUIDv7)}
  errors: BLOCK_NOT_FOUND, BLOCK_PINNED, VALIDATION_FAILED

hearth.query_data
  input: {page_id: string, block_id?: string, filters?: object, limit?: number}
  success: {records: array}
  errors: PAGE_NOT_FOUND

hearth.propose_block
  input: {
    page_id: string,
    block_type: 'table' | 'counter' | 'list' | 'note' | 'chart',
    config: object,
    rationale: string
  }
  success: {proposal_id: string}
  errors: PAGE_NOT_FOUND, INVALID_BLOCK_TYPE

hearth.pin_block
  input: {block_id: string}
  success: {ok: true}
  errors: BLOCK_NOT_FOUND, PIN_NOT_ALLOWED
  note: PIN_NOT_ALLOWED is always returned because MCP is the agent; only the UI can pin.

hearth.unpin_block
  input: {block_id: string}
  success: {ok: true}
  errors: BLOCK_NOT_FOUND, PIN_NOT_ALLOWED
```

### Pin semantics (locked)

A pinned block rejects ALL of the following: record writes (`add_record` returns `BLOCK_PINNED`), config writes (`update_block` returns `BLOCK_PINNED`), deletes (`delete_block` returns `BLOCK_PINNED`), reorders (`reorder_blocks` returns `BLOCK_PINNED`). New proposals against the page are unaffected — the agent can still propose new blocks even if existing blocks are pinned. **Pinning is user-only:** both `hearth.pin_block` and `hearth.unpin_block` from MCP return `PIN_NOT_ALLOWED`. The agent can suggest ("you might want to pin the auto-imported rows") but cannot do it itself.

### Proposal data model

`proposals` table (see DDL above) with state machine: `proposed → accepted | rejected | expired | superseded`. Auto-expire after 7 days via a sweeper that runs once per hour via a `tokio::time::interval` independent of app launch.

**Acceptance placement rule:** when the user accepts a proposal via `AcceptProposal { id }`, the new block is appended to the **end** of the page's layout (highest `ordinal + 1`). The block lands at the bottom of the canvas in the active page. Rationale: proposals arrive as the agent's ideas; the user can drag them to a new position if they don't want them at the bottom. This avoids the agent choosing placement on the user's behalf.

### Update propagation

`applyMutation` (in Rust) calls `app_handle.emit("data-changed", {record_id, table_name, lamport_ts})` after committing each transaction. The Tauri webview subscribes to this event in `main.tsx`; on receipt, it invalidates the affected react-query cache keys and triggers a re-fetch. **No polling.** Latency from `applyMutation` return to UI re-render: ~5-10ms (event round-trip + React state update).

#### Update propagation paths

There are two paths into `applyMutation`, with different update propagation:

| Path | How UI learns of change | Latency | Scope |
|---|---|---|---|
| **In-process chat** | Tauri event (`data-changed`) | <10ms | Most common path; covers the embedded Hermes subprocess |
| **External MCP client** | Polling `event_log` for new rows, 1-second interval | ~1s | External clients (Claude Code, Codex) when embedded MCP server is enabled |

Both paths converge at `applyMutation`; they differ only in how the UI is notified afterward. The polling fallback for external clients exists because external processes don't share the in-process broadcast channel.

## Premises

P1. This is a personal tool, not a startup; monetization and user growth are not in scope. *(Source: D1.)*

P2. The primary pain is "no visualization during agent conversation" — the agent and the data should be in the same working surface. *(Source: original message + pivot clarification.)*

P3. UX-shape = a single Tauri window with three zones: chat sidebar (left), page tree (right), widget canvas (center). The user and the agent are **co-tenants** of the same window. The agent can edit layouts and data through direct in-process tool calls; the user can edit through the UI. **Blocks can be "pinned"** so neither user nor agent can modify them without explicit unpin. Pinning is a user-only safety mechanism. *(Source: D3 choice B + D7 reformulation + plan-eng-review pivot.)*

P4. MVP = local Tauri app, no VPS/cloud/sync in v1. Data layer is designed so VPS-sync is a +1 transport adapter, not a rewrite. *(Source: D4/D5 choice C.)*

P5. First-queue domains: finance, health, fitness, tasks, email, habits. *(Source: original message.)*

P6. The six domains are the *initial* set of pages, but the user can create custom pages in the page tree (this is the "подпапки" feature the user described). *(Source: pivot message — "можно было бы создавать свои вкладки как в notion и подпапки".)*

## Approaches Considered

### Approach A: Fork `fathah/hermes-desktop`, add page tree and widget canvas as new panels

**Effort:** M · **Risk:** Med-High · **Completeness:** 7/10

Pros:
- Already-working Electron app with chat UI, sessions, profiles, multi-provider.
- Already-working installer + auto-update.
- Kanban panel exists — usable as reference for the tasks domain.
- Already SQLite under the hood.

Cons:
- Inherits 22 slash-commands, Kanban logic, persona editor, memory-providers — extra cognitive load.
- Customization = manual merge with upstream; merge hell.
- Electron ≈ 150MB RAM baseline; Tauri could give 20MB.
- The user's actual UX is "single window with three zones" — `fathah/hermes-desktop` has chat + sidebar + settings, but no page tree or widget canvas. We'd be adding two major panels to their architecture.
- The user's three-zone UX is closer to building fresh than extending a chat-only app.

### Approach B: Single-process Tauri, embedded chat + embedded MCP (RECOMMENDED)

**Effort:** XL · **Risk:** Med · **Completeness:** 10/10

Pros:
- Matches the user's three-zone UX directly: one Tauri window with sidebar (chat), right panel (page tree), center (canvas).
- Single process → no cross-process coordination, no separate MCP binary, no BEGIN IMMEDIATE concerns.
- Embedded MCP server still exists (for external clients like Claude Code), but in-process calls are ~50x faster.
- Tauri = 20MB RAM, native feel.
- Same React bundle → Tauri desktop + later web-deploy (post-MVP).
- No legacy, no merge conflicts.

Cons:
- 1-2 weeks on Tauri bootstrap, IPC contract, embedded Hermes runtime integration. With AI help, compressible to ~1 week.
- Own installer (Tauri CLI handles it; ad-hoc codesign for Gatekeeper).
- Chat UI is non-trivial (streaming, markdown, tool-call display, cancel) — ~2 weeks alone, not "simple".
- Embedding Hermes Agent as a Rust library is an open question (TBD during implementation).

### Approach C: Use `pewdiepie-archdaemon/odysseus` as the base (self-hosted web app) + add chat sidebar

**Effort:** XL · **Risk:** High · **Completeness:** 8/10

Pros:
- Already has a page-tree + canvas model (closest to user's UX among the three references).
- Python stack is fast to iterate in.

Cons:
- Not desktop — it's a self-hosted web app on `localhost:7000`. User said "десктоп и веб приложение" — desktop is the primary surface.
- AGPL-licensed; user would need to comply.
- Adding a chat sidebar means building a real-time UI on top of their server-rendered architecture.
- Doesn't solve the "single window" UX — the chat would be a web panel inside a web app, not a native desktop chat.

## Recommended Approach

**Approach B — Single-process Tauri with embedded chat and embedded MCP.** The user's three-zone UX is the load-bearing constraint, and only B delivers it without a major retrofit. C is closest in spirit (odysseus already has pages + canvas) but loses the desktop-first UX. A has the right form factor (desktop) but the wrong shape (chat-only, no pages/canvas).

The single-process architecture is a major simplification over the prior design. We trade a small bit of "I can also point external MCP clients at this" (which is preserved as the embedded MCP server) for a lot of "no cross-process coordination, no separate binary, no IPC latency."

## Testing

Test plan for v1, covering the three layers of the system.

### Unit tests (Rust, `hearth-core`)

- **`applyMutation` per-variant correctness:** for each `Mutation` variant (Create/Update/Delete for each table, plus PinBlock/UnpinBlock/AcceptProposal/RejectProposal/ExpireProposal), write a test that calls `applyMutation` with a known input, asserts the resulting DB state and `event_log` row, and asserts the return value of `MutationResult`.
- **Pin invariants:** tests for `BLOCK_PINNED` returned on add_record/update_block/delete_block/reorder_blocks against a pinned block; `PIN_NOT_ALLOWED` returned when `agent_id != 'user'` for PinBlock/UnpinBlock.
- **Transaction atomicity:** test that a failing mutation mid-transaction leaves no partial state (e.g., `applyMutation` that hits a constraint violation during target-table mutation must roll back the lamport bump and event_log insert).
- **Event log payload shape:** tests for `create` (full row in `after`), `update` (partial fields in `after`), `delete` (`id` + `before_summary`).
- **Lamport counter:** tests for monotonic increment within transaction, `BEGIN IMMEDIATE` serialization between concurrent writers.
- **Hash chain:** test that `prev_hash` is `null` for genesis events and `SHA-256(previous row)` for subsequent events.
- **Backup/restore:** test the round-trip: create DB → backup with passphrase → restore → verify same DB state. Test that the backup archive does NOT contain `key.txt`.

### Integration tests (Rust, full app)

- **First-launch onboarding:** simulate first launch (no DB, no keychain entry) → verify key is generated → verify keychain entry created → verify DB created with PRAGMA key.
- **Workspace seed:** verify that the opt-in wizard produces a workspace + 6 pages (when user accepts) or empty workspace (when user skips).
- **Hermes subprocess lifecycle:** spawn Hermes subprocess, send `initialize` JSON-RPC, expect 5 hearth.* tools in `tools/list` response. Send `tools/call` for `hearth.add_record`, expect `MutationResult::Created(uuid)`.
- **MCP server toggle:** verify server is OFF by default; toggling ON binds the port and shows the bearer token; toggling OFF unbinds.

### End-to-end tests (manual + Tauri webview harness)

- **Chat→tool→event_log→UI round trip:** start app → click chat sidebar → type "log today's weight as 82.3" → verify Hermes invokes `hearth.add_record` → verify a new `records` row appears → verify the counter block on the fitness page shows 82.3 → verify `sqlite3` CLI shows a new `event_log` row with `agent_id='hermes'`.
- **Pin enforcement:** create a counter block → pin it → type in chat "update weight to 99" → verify the chat shows an error from Hermes about the block being pinned.
- **Proposal flow:** type in chat "propose a bar chart of expenses by category for this week" → verify a banner appears on the finance page → click Accept → verify the bar chart block appears at the bottom of the layout.
- **Backup/restore:** trigger backup → save archive → quit app → delete DB → restore from archive → verify all pages, blocks, records, pins, and event_log are intact.

### Tauri webview unit tests

- Block type config validation: one test per block type with a valid config (passes) and an invalid config (fails Zod).
- PageTree reorder: drag-reorder updates ordinals correctly, no two siblings share an ordinal.
- Three-zone layout state: switching the active page updates the canvas, deselecting the active page leaves it empty, etc.
