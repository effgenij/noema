## Problem Statement

Чат с агентом неудобен как рабочая поверхность для жизни: ответы с данными тонут в истории, нет «открыть вкладку и увидеть сегодняшее». Нужна визуализация перед глазами — дашборды, задачи, тренировки, конспекты курсов, — с которыми агент работает в том же окне. Пользователь живёт в Hermes Desktop и хочет единый личный lifeOS: данные + представления + агентная обработка (учебные конвейеры, тренировки, финансы, проекты) в одном месте, с интеграцией будущих агентов (openclaw и др.).

## What Makes This Cool

Первый «whoa»: **агент и данные — соседи по одному окну.** Сказал в чате «добавь расход 500р» — канбан/таблица рядом обновилась; открыл вкладку «Тренировки» — видишь сегодняшее; спросил «что по деньгам за неделю» — виджет дашборда перерисовался. У Tana/Taskade это платная фича поверх облака; здесь — свойство среды.

Второй: **конвейер «видеокурс → курс»** (этап 2): скормил курс без учителя — получил конспекты, задания, практику, прогресс в базе, знания в документах. Нигде нет как first-class фичи.

Третий: **данные структурированы с первого дня** (SQLite), а не markdown, который агент парсит; при переходе к standalone-приложению (D1) мигрируют данные, а не архитектура.

## Constraints

- Личный тул, один пользователь; расширяемость важнее полировки.
- Плагин Hermes Desktop = этап 1; standalone cortex — только по явному триггеру (D1).
- Интеллект — у агента (скиллы, cron, боты, память); плагин владеет только данными и вьюхами.
- Чат не дублируем: window.hermes.send ≤500 символов, без стриминга — встроенный чат в страницу плагина невозможен и не нужен.
- Графики: без chart-библиотек (SDK их не резолвит) — собственные SVG-компоненты.
- Desktop-половина — без JSX: только импорты `@hermes/plugin-sdk`, `react`, `react/jsx-runtime` — писать через `jsx()`/`jsxs()` из `react/jsx-runtime`, JSX-синтаксис в `plugin.js` не скомпилируется.
- Данные: один SQLite через `plugin_db` (WAL); состояние никогда не в папке плагина, только в data-dir.

## Premises

P1. Личный тул; плагин — этап 1, standalone по явному триггеру; данные/API проектируются переносимыми. (D1)
P2. Главная боль — «не вижу данные, с которыми работает агент». (подтверждено во всех трёх итерациях)
P3. Интеллект у агента; плагин = данные + вьюхи; кросс-доменные сценарии агент делает через инструменты. (согласовано)
P4. Ядро v1 — общие «базы» + фиксированный набор вьюх (список/таблица/канбан/календарь/карточки/прогресс) + хоум-дашборд; НЕ дженерик-движок Notion. (D2)
P5. UX: дерево баз слева внутри страницы плагина + вьюха по центру; чат Hermes — существующий, рядом; не дублируем. (D3)
P6. Модель данных — гибрид: строгие схемы для количественных доменов, JSON-поля для документов. (D6)
P7. Стартовые модули v1: tasks + notes + habits; learning/body/money/feed — этапы 2+. (D7)

## Approaches Considered

### Approach A: Каркас + базы + вьюхи + хоум (выбрано, D2)
Сводка: гибридная папка плагина (`~/.hermes/plugins/cortex/`: plugin.yaml + __init__.py + skills/ + dashboard/plugin_api.py + desktop/plugin.js). Ядро: «базы» (типизированные таблицы), фиксированный набор вьюх, хоум-дашборд-грид. Стартовые модули tasks/notes/habits.
Effort: M (недели) · Risk: Low-Med · Completeness: 9/10
Pros: общий фундамент всех будущих доменов; первая польза за недели; ничего не выбрасывается.
Cons: учебный конвейер — этап 2; нет мгновенной проверки самой рискованной гипотезы.

### Approach B: Learning-конвейер первым (отклонено)
Effort: M-L · Risk: High · Completeness: 5/10
Pros: сразу проверяет главную гипотезу; главный болевой сценарий.
Cons: временное хранилище «под курсы» → переделка; каркас всё равно нужен → двойная работа.

### Approach C: Standalone сразу (Hearth) (отклонено, архивировано)
Effort: XL · Risk: Med · Completeness: 10/10
Pros: полный контроль трёх зон; дизайн прошёл eng-review.
Cons: месяцы до пользы (доказано: с июня не построено); чат-UI с нуля; MCP-интеграция руками.

## Recommended Approach

**A — каркас + базы + вьюхи + хоум, стартовые модули tasks/notes/habits.** Рекомендация D2 подтверждена пользователем. Learning-конвейер — этап 2 поверх готовых баз.

Архитектура (из исследования 23.08, все ограничения проверены по исходникам):
- Ядро: SQLite-базы (`plugin_db`), FastAPI-бэкенд (`/api/plugins/cortex/`), страницы в сайдбаре (`ROUTES_AREA` + `SIDEBAR_NAV_AREA`), хоум-грид виджетов, `::preview`-виджеты в чате с `window.hermes.send()`.
- Агентные инструменты (`ctx.register_tool`): CRUD над базами — агент пишет/читает те же данные, что и UI.
- Обновление UI при записи агентом: **polling активной вьюхи раз в 3с — основной механизм** (API эмиссии события гейтвея из Python-инструмента не существует: `ctx.emit` — внутрипроцессная шина плагин↔плагин, до десктопа не доходит; `host.onEvent` видит только события ядра гейтвея). `host.onEvent` — только для штатных событий гейтвея (`sessions.changed` и т.п.). Ручные правки из UI перерисовывают локально без ожидания polling.
- Данные: гибрид (P6) — строгие таблицы (tasks, habits) + JSON-документы (notes); идентификаторы — UUIDv7 через пакет `uuid6`/`uuid7` (в системном Python 3.9 `uuid.uuid7()` нет; альтернатива — ручная генерация: 48-бит timestamp + случайные биты). Бэкап — через SQLite backup API (`sqlite3 .backup` / `Connection.backup()`), не простое копирование файла: при активном WAL копия может быть неконсистентной.
- Вьюхи v1: список/таблица, канбан (tasks), календарь, документы-карточки (notes), стрики (habits). Виджеты хоума: задачи на сегодня, стрики, счётчик inbox-заметок.
- Переносимость (P1): схема БД и REST-маршруты не зависят от плагинного SDK — standalone-переезд = замена транспортного слоя.

## Open Questions

1. Форма дерева слева: папки внутри баз (проекты → задачи) или дерево произвольных страниц? *(дефолт: папки внутри баз; дерево страниц — v2)*
2. Двусторонняя связь «виджет в чате ↔ база»: через `data-hermes-send` (промпт агенту) или прямые `ctx.rest` из preview-iframe? *(дефолт: промпт агенту — проще и безопаснее)*
3. Синхронизация 3 машин: бэкенд+SQLite только в профиле VPS-гейтвея (одна каноническая копия, десктоп на Mac/Windows достукивается по сети) — подтвердить при настройке. *(исследование 23.08, §3 машины)*
4. Приватность: всё локально/на своём VPS — ок? *(дефолт: да)*

## Success Criteria

MVP «готов», когда пользователь может:
1. Открыть Hermes Desktop → страницы Cortex в сайдбаре: Home, Tasks, Notes, Habits.
2. В Tasks: канбан с задачами; добавить задачу руками И из чата («добавь задачу X на среду») — оба пути пишут одну базу, UI обновляется.
3. В Notes: создать заметку, видеть её в дереве слева, редактировать; агент добавляет конспект в заметку из чата.
4. В Habits: чек-ин дня, стрики, спарклайн.
5. Хоум-дашборд: виджеты «задачи на сегодня», «стрики», «свежие заметки» — данные из всех трёх баз.
6. Виджет в чате (`::preview`): задача-карточка, кнопка «завершить» отправляет промпт агенту (дефолт OQ2) → база обновляется → страница перерисовывается. *(Зависит от закрытия OQ2 до старта T5.)*
7. Перезапуск приложения — все данные на месте (SQLite в data-dir).
8. Новый модуль (например, workouts) добавляется как схема + вьюхи + инструменты без переписывания ядра — проверка расширяемости.
