## Problem Statement

When talking to an AI agent (Hermes, Claude Code, Codex, anything), the conversation is text-only. The agent acts on your data, but you can't *see* the data it's acting on in the same surface. You scroll back through chat logs to remember "wait, what was my average spend last week?" or "did I log today's weight?" — even when the agent just edited that record two minutes ago.

The user has six life domains they want to operate on with an agent: finance, health, fitness, tasks, email, habits. They want one surface where **they** configure the views, the **agent** can edit the views and the data, both work over the same layout, and neither can silently break what the other built. Pinned blocks are the seatbelt.

## What Makes This Cool

The "whoa" is **bidirectional control over the same layout**. Most agent UI is asymmetric — agent commands, UI displays, or UI commands, agent reads. Here, both actors are first-class editors of a shared layout-store. You drag a chart onto your finance dashboard; the agent reorders it because it sees a better grouping; you pin it so neither of you touches it without an unpin; the agent later proposes a new block that appears as a soft suggestion you can accept or reject.

The second "whoa" is **layout-as-data, not layout-as-document**. Notion treats each page as a document. Here, the layout is a CRDT-ready data structure that the agent reasons about and edits programmatically. The rendering is a function of the data, not a separate artifact. This means the agent can answer "where is my March weight chart?" by querying the layout-store, not by parsing a doc.

The third "whoa" is **desktop (and later web) from one bundle**. Tauri + React means the same code ships to a native macOS app now, and later the same bundle can deploy to a static host as a read-only web view. The agent doesn't care which surface it's talking to — it talks to the data layer via MCP.

## Constraints

- **Personal tool, not a startup.** No users besides the builder. No monetization. No growth. (Premise P1.)
- **Local-first MVP.** No VPS, no cloud, no cross-device sync in v1. Data lives on the mac. (Premise P4.)
- **VPS-sync later is a hard requirement of the design**, not an afterthought. The data layer must be designed so adding VPS is a transport adapter, not a rewrite. This drives two non-negotiable decisions: (a) every record has a **ULID/UUIDv7** identifier (no autoincrement integers — they collide across replicas), and (b) every mutation appends to a **per-table event log** with `(record_id, lamport_ts, op_type, payload, prev_hash)` so a future replicator can replay/merge. See "Data Layer Decisions" below for the concrete model.
- **The six domains already have decent solutions** (Apple Health, banking apps, Mail.app, Reminders). Hearth's value isn't replacing those — it's giving the agent a structured view across them and giving the user a single dashboard.
- **The builder already uses Hermes** on macOS — MCP-based integration is preferred over subprocess spawning.
- **The builder is opinionated about taste** — wants no WYSIWYG bloat, prefers config/code-first when reasonable, prefers deliberate pinning over implicit safety.
- **Single-machine MVP, two cooperating processes (`hearth-app` UI and `hearth-mcp` agent).** They share the SQLite file and coordinate through SQLite's WAL-mode locking + the persisted `meta.lamport_counter`. There are no concurrent writes to the *same* record at the same time in v1 (single user, single agent); serialization happens via SQLite's write lock acquired with `BEGIN IMMEDIATE`. No CRDT machinery runs at v1; CRDT-readiness here means "the event log is shaped so a future replicator can do merge logic", not "we run a CRDT runtime now".

## Data Layer Decisions

These are locked by the VPS-future requirement. They are not negotiable for v1.

### Identifiers

- Every row in `domains`, `layouts`, `blocks`, `records`, `pins`, `proposals` uses **UUIDv7** (sortable by creation time, globally unique, no collision across replicas). ULID is acceptable; UUIDv4 is not (no time-ordering hurts query planning).
- Foreign keys reference UUIDv7s.
- SQLite `PRAGMA foreign_keys = ON;` enforced.

### Lamport counter (persisted, cross-process)

The lamport counter is **a single row in a `meta` table**, NOT an in-memory variable. This is essential because `hearth-app` (UI writes) and `hearth-mcp` (agent writes) run as separate processes; in-memory counters would collide.

```
meta(
  key TEXT PRIMARY KEY,
  value TEXT
)
-- row: ('lamport_counter', '0')
```

`applyMutation` reads-and-increments the counter inside the same transaction as the event_log insert:

```
BEGIN IMMEDIATE;
  UPDATE meta SET value = CAST(CAST(value AS INTEGER) + 1 AS TEXT) WHERE key = 'lamport_counter';
  INSERT INTO event_log (lamport_ts = (SELECT value FROM meta WHERE key = 'lamport_counter'), ...);
  -- mutate target table(s)
COMMIT;
```

`BEGIN IMMEDIATE` (not `BEGIN`) acquires a write lock at the start of the transaction so concurrent writers serialize through SQLite's locking, not through racing on the meta row.

### SQLite schema (DDL for v1)

```sql
-- meta: singletons (lamport counter, schema version, etc.)
CREATE TABLE meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);

-- domains: top-level life areas
CREATE TABLE domains (
  id         TEXT PRIMARY KEY,        -- UUIDv7
  slug       TEXT NOT NULL UNIQUE,    -- 'finance' | 'health' | 'fitness' | 'tasks' | 'email' | 'habits'
  name       TEXT NOT NULL,           -- display name (user-editable)
  icon       TEXT,                    -- emoji or icon name
  created_at TEXT NOT NULL,           -- ISO 8601 UTC
  deleted_at TEXT                     -- soft-delete; null = active
);
CREATE INDEX idx_domains_slug ON domains(slug) WHERE deleted_at IS NULL;

-- layouts: per-domain layout container; v1 uses 1:1 (one active layout per domain)
CREATE TABLE layouts (
  id         TEXT PRIMARY KEY,
  domain_id  TEXT NOT NULL UNIQUE REFERENCES domains(id) ON DELETE CASCADE,
  -- blocks are stored separately and referenced by layout_id; ordering via ordinal column
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- blocks: individual widgets in a layout
CREATE TABLE blocks (
  id           TEXT PRIMARY KEY,
  layout_id    TEXT NOT NULL REFERENCES layouts(id) ON DELETE CASCADE,
  block_type   TEXT NOT NULL,    -- 'table' | 'counter' | 'list' | 'note' | 'chart'
  config       JSON NOT NULL,    -- block-type-specific config
  ordinal      INTEGER NOT NULL, -- position in layout (lower = first)
  title        TEXT,             -- user-set title
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);
CREATE INDEX idx_blocks_layout ON blocks(layout_id, ordinal);

-- records: data rows belonging to a block
CREATE TABLE records (
  id          TEXT PRIMARY KEY,
  block_id    TEXT NOT NULL REFERENCES blocks(id) ON DELETE CASCADE,
  fields      JSON NOT NULL,    -- block-type-specific data
  amount      REAL,             -- finance: amount; null otherwise
  currency    TEXT,             -- ISO 4217: 'RUB' | 'USD' | 'EUR' | ...; null if not monetary
  occurred_at TEXT NOT NULL,    -- ISO 8601 UTC
  tz          TEXT,             -- IANA timezone at occurrence (e.g. 'Europe/Moscow')
  created_at  TEXT NOT NULL
);
CREATE INDEX idx_records_block_time ON records(block_id, occurred_at DESC);

-- pins: separate table for fast pin-state queries; a pinned block cannot be edited/deleted/reordered
CREATE TABLE pins (
  block_id  TEXT PRIMARY KEY REFERENCES blocks(id) ON DELETE CASCADE,
  pinned_at TEXT NOT NULL,
  pinned_by TEXT NOT NULL          -- 'user' | 'hermes' (hermes cannot pin, only user can; this is a constraint)
);
-- v1 invariant: pins are created only by user; MCP `hearth.pin_block` returns PIN_NOT_ALLOWED.

-- proposals: agent-suggested blocks; see Proposals section
CREATE TABLE proposals (
  id          TEXT PRIMARY KEY,
  domain_id   TEXT NOT NULL REFERENCES domains(id) ON DELETE CASCADE,
  block_type  TEXT NOT NULL,
  config      JSON NOT NULL,
  rationale   TEXT NOT NULL,
  status      TEXT NOT NULL CHECK (status IN ('proposed','accepted','rejected','expired','superseded')),
  created_at  TEXT NOT NULL,
  expires_at  TEXT NOT NULL,
  decided_at  TEXT,
  decided_by  TEXT CHECK (decided_by IN ('user','auto-expire'))
);

-- event_log: see Event log section
CREATE TABLE event_log (
  id          TEXT PRIMARY KEY,
  record_id   TEXT NOT NULL,
  table_name  TEXT NOT NULL,
  op_type     TEXT NOT NULL CHECK (op_type IN ('create','update','delete')),
  payload     JSON NOT NULL,
  prev_hash   TEXT,                -- null for genesis event of a record_id
  lamport_ts  INTEGER NOT NULL,
  agent_id    TEXT NOT NULL CHECK (agent_id IN ('user','hermes')),
  created_at  TEXT NOT NULL
);
CREATE INDEX idx_event_log_record ON event_log(record_id, lamport_ts);
CREATE INDEX idx_event_log_time ON event_log(created_at DESC);
CREATE INDEX idx_event_log_lamport ON event_log(lamport_ts);

-- Index for proposal polling (UI watches status='proposed' rows)
CREATE INDEX idx_proposals_status_expires ON proposals(status, expires_at);
```

### `event_log.payload` shape

For replicator LWW-per-field to be deterministic, `payload` is shaped consistently:
- `create`: `{"after": {<full new row as JSON object excluding id>}}`
- `update`: `{"after": {<new field values, full record not partial>}}`
- `delete`: `{"id": "<uuidv7>", "before_summary": {<snapshot of the row for conflict resolution>}}`

The replicator's LWW merge reads `payload.after` (or `payload.before_summary` for deletes) and compares field-by-field against its local copy, picking the field value from the event with higher `(lamport_ts, agent_id)` lexicographic order.

### Event log (the "WAL" — see Naming Note below)

Every mutation appends a row to `event_log` BEFORE the corresponding table write. Both happen in the same SQLite transaction so they commit atomically.

```
event_log(
  id           UUIDv7 PK,
  record_id    UUIDv7,         -- the entity being mutated
  table_name   TEXT,           -- 'blocks' | 'records' | 'pins' | 'layouts' | ...
  op_type      TEXT,           -- 'create' | 'update' | 'delete'
  payload      JSON,           -- the new field values (for create/update) or {id} (for delete)
  prev_hash    TEXT,           -- SHA-256 of the previous event_log row for this record_id (chain integrity)
  lamport_ts   INTEGER,        -- monotonic counter, incremented before each mutation
  agent_id     TEXT,           -- 'user' | 'hermes' | <other-agent-name>
  created_at   TEXT            -- ISO 8601 UTC, informational only (lamport_ts is authoritative for ordering)
)
```

### Merge semantics (for future replicator, not v1 runtime)

For each `(record_id, table_name)`, the event_log forms a per-record hash chain. A future VPS-sync replicator merges two replicas by:

1. Compare `lamport_ts` of the latest known event per record on each side.
2. If both sides have events for the same `(record_id, lamport_ts)`, the events are identical (same chain position → same content) OR they conflict (different content). Conflict resolution = **LWW per field** by `(lamport_ts, agent_id)` lexicographic order, with the losing branch's payload preserved as a "merge candidate" the user can review.
3. If chains diverge (one side has events the other doesn't), replay missing events in `lamport_ts` order.

This is not a true CRDT (no commutative ops, no state-based merge), but it is "CRDT-ready" in the sense that the log is shaped to support a deterministic merge. A future iteration could swap the merge function for Yjs/Automerge if conflict rates demand it.

### SQLite journal mode

`PRAGMA journal_mode = WAL;` (SQLite's built-in WAL journal — this is the DB-engine journal, NOT the same as the application's `event_log`). For clarity, **"event log" = application-level append-only log of mutations; "WAL" = SQLite's journal mode**. These are two different things and must not be conflated.

### Encryption-at-rest

SQLite database encrypted with **SQLCipher** (`PRAGMA key = '...'`) using a 32-byte key. **Key lifecycle:**

1. **First launch (no existing DB):** generate 32 random bytes via `SecRandomCopyBytes`, write key to macOS keychain via `security add-generic-password -s hearth.db -a sqlcipher-key -w <key>`, then open DB with `PRAGMA key = "x'<hex>'"`.
2. **Subsequent launches:** read key from keychain, open DB with key. If keychain read fails → fail fast with a clear error ("Cannot unlock hearth.db. Keychain access denied.") — never silently create a new DB.
3. **Backup portability:** the backup is a `.tar.gz` containing `hearth.db` AND `key.txt` (the key in hex). Without the key, the DB is unreadable. The UI shows a "Backup now" button that prompts for a destination path and produces this archive. The UI documents this prominently: **"Losing the key = losing the data. Keep both safe."**
4. **Connection-init flow:** `tauri-plugin-sql` takes a connection URL. We pass `sqlite://...?mode=ro&key=x'ABCDEF...'` for reads; for writes we go through `hearth-core::applyMutation()` (NOT through the plugin), which handles the key via a single `PRAGMA key` after `sqlite3_open_v2`. Reads can use the plugin; writes must use `applyMutation`.

The plugin-read / `applyMutation`-write split is critical: if the UI calls the plugin for writes, it bypasses the event log and breaks the audit trail + future VPS-sync design. Document this split in CONTRIBUTING.md.

### SQLite client

Use **`tauri-plugin-sql`** (rusqlite under the hood) instead of `better-sqlite3` directly. Avoids the Vite N-API/externalize footgun in Tauri 2 dev server. SQLCipher is available as a rusqlite feature flag.

### Migrations

- `PRAGMA user_version` holds the schema version number.
- Migration scripts are SQL files in `src-tauri/migrations/v001_initial.sql`, `v002_add_proposals.sql`, etc., each wrapped in `BEGIN; ... COMMIT;`.
- On app launch, read `user_version`, run unapplied migrations in order, bump `user_version`.
- **Drizzle-kit is used for schema authoring (typed JS reads from the TypeScript side) — SQL migrations are authoritative.** When you change the schema, write the migration SQL by hand, then update the Drizzle schema TS to match. They are not generated from each other.
- **Migration race avoidance:** `hearth-app` and `hearth-mcp` both check `user_version` on startup. They take a process-level SQLite write lock (via `BEGIN IMMEDIATE`) at startup; if either detects an out-of-date `user_version`, it runs the migration within that lock. The other process blocks until the migration commits. This is safe because migrations are infrequent (schema changes only) and the lock is brief. Document in CONTRIBUTING.md: "Quit the agent before running a version upgrade."

## MCP Transport

MCP is **a separate Rust binary** (`hearth-mcp`), not embedded inside the Tauri app. Here's why and how:

**Why separate binary, not in-process:**
- Hermes (and other MCP-aware clients) connect to MCP servers via stdio JSON-RPC. Tauri apps don't expose stdio servers; they expose HTTP/WebSocket IPC over `tauri://localhost`.
- A standalone binary is portable: works with Hermes, Claude Code, Codex, any MCP client. The Tauri app doesn't need to be running for the agent to talk to Hearth data.
- Cleaner boundaries: `hearth-mcp` is stateless from its own perspective; it just reads/writes the SQLite file using the same `applyMutation` function the Tauri app uses (shared Rust crate).

**Architecture:**

```
hearth-app (Tauri)
  ├── React UI
  ├── Tauri commands → applyMutation() ─┐
  └── event_log watcher (poll 200ms) ←─┤
                                        │
hearth.db (SQLite + SQLCipher)         ←┤  ← shared file
                                        │
hearth-mcp (standalone Rust binary)    ←┘
  ├── stdio JSON-RPC MCP server
  ├── Tools: hearth.add_record, hearth.query_data,
  │         hearth.propose_block, hearth.pin_block, hearth.unpin_block
  └── applyMutation() (same crate as app)
```

**Tool schemas (v1, JSON-schema form):**

```json
hearth.add_record
  input: {
    domain: string (one of: finance, health, fitness, tasks, email, habits),
    block_id: string (UUIDv7 of the target block),
    fields: object (block-type-specific; e.g. {amount: number, currency: string, category: string, note: string} for finance)
  }
  success: {record_id: string (UUIDv7)}
  errors: BLOCK_NOT_FOUND, BLOCK_PINNED, VALIDATION_FAILED

hearth.query_data
  input: {domain: string, block_id?: string, filters?: object, limit?: number}
  success: {records: array}
  errors: DOMAIN_NOT_FOUND

hearth.propose_block
  input: {
    domain: string,
    block_type: 'table' | 'chart' | 'list' | 'counter' | 'note',
    config: object,
    rationale: string (why the agent thinks this block is useful)
  }
  success: {proposal_id: string}
  errors: DOMAIN_NOT_FOUND, INVALID_BLOCK_TYPE

hearth.pin_block
  input: {block_id: string}
  success: {ok: true}
  errors: BLOCK_NOT_FOUND, PIN_NOT_ALLOWED
  note: PIN_NOT_ALLOWED is always returned because MCP is the agent; only the UI can pin. (Unpinning is also user-only for symmetry.)

hearth.unpin_block
  input: {block_id: string}
  success: {ok: true}
  errors: BLOCK_NOT_FOUND
```

**Pin semantics (locked):** A pinned block cannot be edited, deleted, OR reordered. The agent's tools return `BLOCK_PINNED` for any write attempt against a pinned block. To modify, unpin first. **Pinning is user-only:** `hearth.pin_block` and `hearth.unpin_block` from MCP both return `PIN_NOT_ALLOWED` because pin is a safety mechanism the user controls unilaterally. The agent can suggest ("you might want to pin the auto-imported rows") but cannot do it itself. Pinned blocks do not block new proposals; they only block edits to themselves.

**Proposal data model:**

```
proposals(
  id            UUIDv7 PK,
  domain_id     UUIDv7 FK,
  block_type    TEXT,    -- 'table' | 'chart' | 'list' | 'counter' | 'note'
  config        JSON,    -- block-type-specific config
  rationale     TEXT,    -- agent's one-line reason
  status        TEXT,    -- 'proposed' | 'accepted' | 'rejected' | 'expired' | 'superseded'
  created_at    TEXT,    -- ISO 8601 UTC
  expires_at    TEXT,    -- ISO 8601 UTC (default: +7 days)
  decided_at    TEXT,    -- null until status changes
  decided_by    TEXT     -- 'user' | 'auto-expire'
)
```

UI shows a banner per domain when `status = 'proposed'` rows exist, with preview + accept/reject. On accept, the proposal row is converted to a normal block row (record_id preserved); on reject/expire, status flips and the row stays for audit.

**Update propagation (~1 second target):**
The Tauri app watches the `event_log` table for new rows. Polling interval 200ms with `?lamport_ts > last_seen_lamport` query; new rows trigger react-query cache invalidation for affected keys. Polling is cheap with WAL-mode SQLite (single indexed range scan per tick). UI re-renders affected blocks/records on cache refresh.

**Atomicity of `applyMutation`:**
A single SQLite transaction:
```
BEGIN IMMEDIATE;
  UPDATE meta SET value = CAST(CAST(value AS INTEGER) + 1 AS TEXT) WHERE key = 'lamport_counter';
  INSERT INTO event_log (lamport_ts = (SELECT value FROM meta WHERE key = 'lamport_counter'), ...);
  -- mutate target table(s)
COMMIT;
```
If the process dies between BEGIN and COMMIT, SQLite rolls back. No partial state. No replay needed at restart because the transaction either fully committed or fully rolled back.

**`applyMutation` signature (Rust trait):**

```rust
pub enum Mutation {
    CreateDomain { slug: String, name: String, icon: Option<String> },
    UpdateDomain { id: Uuid, fields: serde_json::Value },
    DeleteDomain { id: Uuid },  // soft-delete
    CreateBlock { layout_id: Uuid, block_type: BlockType, config: serde_json::Value, title: Option<String>, ordinal: i32 },
    UpdateBlock { id: Uuid, fields: serde_json::Value },
    ReorderBlocks { layout_id: Uuid, new_ordering: Vec<Uuid> },
    DeleteBlock { id: Uuid },
    PinBlock { id: Uuid },       // user-only; rejected with PIN_NOT_ALLOWED if agent_id != 'user'
    UnpinBlock { id: Uuid },
    AddRecord { block_id: Uuid, fields: serde_json::Value, amount: Option<f64>, currency: Option<String>, occurred_at: DateTime<Utc>, tz: Option<String> },
    CreateProposal { domain_id: Uuid, block_type: BlockType, config: serde_json::Value, rationale: String },
    AcceptProposal { id: Uuid },
    RejectProposal { id: Uuid },
    ExpireProposal { id: Uuid }, // invoked by the proposal sweeper (see below)
}

pub enum MutationResult {
    Created(Uuid),   // new row's id
    Updated,
    Deleted,
    NoOp,            // e.g. PinBlock on an already-pinned block
}

pub fn applyMutation(m: Mutation, agent_id: &str) -> Result<MutationResult, MutationError>;
```

`agent_id` is passed in (not read from the mutation) so the function can enforce the user-only invariants for `PinBlock` and reject mutations from the wrong source.

**Proposal sweeper (auto-expire):** `hearth-mcp` (or the app on launch) runs `SELECT id FROM proposals WHERE status = 'proposed' AND expires_at < ?` once per hour, and calls `applyMutation(ExpireProposal { id })` for each. This avoids a system timer or cron and keeps the logic in the same code path as user actions.

**MCP registration in Hermes:**

Hermes MCP config (e.g. `~/.hermes/config.yaml`):
```yaml
mcp_servers:
  - name: hearth
    command: /Applications/Hearth.app/Contents/MacOS/hearth-mcp
    transport: stdio
```

(Exact path depends on where the user installs the app bundle. The installer writes a default path; the user can override.)

**UI implementation choices (locked for v1):**
- **State management:** Zustand for editor-local state (drag-in-progress, modals, ephemeral UI); react-query for server-backed data (everything that touches SQLite).
- **Tables:** TanStack Table v8 for the `table` block type.
- **Charts:** Recharts for the `chart` block type.
- **Rich text:** TipTap (ProseMirror-based) for the `note` block type.
- **Drag-and-drop:** dnd-kit for layout drag-add and reorder.
- **Drag-add UX:** each domain's layout canvas has a `+ Add block` button in the top-right; click opens a modal with block-type picker (table / counter / list / note / chart). No drag-from-palette in v1.
- **Gatekeeper:** the unsigned `.app` is ad-hoc signed via `codesign --sign - --deep --force /Applications/Hearth.app`. macOS will still warn on first launch ("unidentified developer"); user right-clicks → Open to bypass. Document in README.

## Premises

P1. This is a personal tool, not a startup; monetization and user growth are not in scope. *(Source: D1 — "лично для себя, монетизация не на горизонте".)*

P2. The primary pain is "no visualization during agent conversation". *(Source: original message — "при общении с агентом нет визуализации. Мне нужна визуализация того о чем говорим. Те же заметки, дашборды, данные которые нужны сейчас".)*

P3. UX-shape = "Notion for life" where **domain = project = layout**. The layout is a bidirectional data object: the user can edit it through a UI editor, and the agent can edit it through an API/data operation, both over the same layout-store. **Blocks can be "pinned"** so neither user nor agent can modify them without explicit unpin. Agent is not the primary UI; UI is not the primary actor. They are two equal editors of one shared structure, with pinning as the safety mechanism. *(Source: D3 choice B + D7 reformulation.)*

P4. MVP = local desktop-only, no VPS/cloud/sync in v1. Data layer is designed for VPS-sync to be a +1 adapter, not a rewrite. *(Source: D4/D5 choice C.)*

P5. First-queue domains: finance, health, fitness, tasks, email, habits. *(Source: original message.)*

## Approaches Considered

### Approach A: Fork + extend `fathah/hermes-desktop`

**Effort:** M · **Risk:** Med-High · **Completeness:** 7/10

Reuses their Electron IPC, electron-builder, auto-updater, settings storage, Kanban panel, sessions DB (FTS5), persona editor, toolsets, slash-commands.

Pros:
- Already-working chat with Hermes Agent + streaming + tool-calls + sessions + multi-provider. Saves ~3 weeks.
- Already-working installer for macOS/Windows/Linux + auto-update through electron-updater.
- Kanban panel exists — usable as reference for the tasks domain.
- Already SQLite under the hood (`db.ts`) — extend the schema, don't build from scratch.

Cons:
- Inherits 22 slash-commands you don't need, Kanban logic, persona editor, multi-provider UX, memory-providers (Honcho/Mem0/etc) — extra cognitive load and bundle size.
- Customization = manual merge with upstream. If they ship every 2 weeks, you live in merge hell.
- Electron ≈ 150MB RAM baseline — slow desktop app where Tauri could give you 20MB.
- Layout-store must be retrofitted into their `db.ts` and Redux-store; bidirectional agent↔UI requires adapting to their event-bus.

### Approach B: Greenfield Tauri + React (RECOMMENDED)

**Effort:** XL · **Risk:** Med · **Completeness:** 10/10

Reuses Hermes Agent as MCP-server (already exists in Hermes GUI), shared design tokens, Hermes skills (gstack is already installed).

Pros:
- Clean data layer from scratch: SQLite + Drizzle, append-only WAL with CRDT-readiness for future VPS-sync.
- Layout-store as a first-class entity: blocks, panels, pinning, bidirectional editing through React renderer + agent tool API.
- Tauri = 20MB RAM instead of 150MB, instant launch, native feel.
- One React bundle → Tauri desktop + web-deploy (same bundle, different shell). Mobile is a future project, not part of v1.
- Hermes already speaks MCP. Hearth ships an MCP **server** (`hearth-mcp`); zero client code needed in Hearth itself.
- No legacy, no merge conflicts.

Cons:
- 1–2 weeks on Tauri bootstrap and IPC contract. With AI help, compressible to ~1 week.
- Own installer (Tauri CLI handles it, but first-time debugging is painful).
- No ready-made chat UI — write your own (but it's simple: streaming + markdown + tool-call display).

### Approach C: Hermes MCP-server + web-only companion

**Effort:** S · **Risk:** Low-Med · **Completeness:** 6/10

Reuses Hermes GUI entirely as chat-host. Next.js/SvelteKit for the web-companion.

Pros:
- Fastest path to working prototype: write an MCP-server + a light web-companion, no desktop stack.
- "Visualization features" live in the Hermes GUI as panels (via MCP UI-extension or artifact-style).
- Minimum own code = minimum own bugs.

Cons:
- "Desktop and web" reduces to "Hermes GUI + web-tab". Visualization is trapped inside someone else's chat-host.
- Editing layouts from Hermes chat = "edit-this-block" commands, not WYSIWYG.
- Bidirectional UI↔agent editing becomes three-level: Hermes → MCP-tool → web-companion → SQLite. Each step is a potential desync.
- Layout-store as a standalone entity is lost — this becomes "a set of panels inside Hermes".

## Recommended Approach

**Approach B — Greenfield Tauri.** The user picked "synthesis, don't copy," which means inheriting 80%-done means inheriting 80% of decisions you don't agree with. The local-first + CRDT-ready WAL + bidirectional layout-store is materially easier to build clean than to retrofit. Tauri gives you desktop + web for free from one React bundle, which closes the "desktop and web" requirement without doubling the work. MCP integration with Hermes is a 1-file client, not a fork, so you stay current.

The XL effort estimate is front-loaded (Tauri bootstrap, IPC contract, SQLite + Drizzle setup, MCP client). Once that's wired, domain work is mostly React components + agent tools.

## Next Steps

Ordered by dependency. Items 1-9 ship for "MVP done" per Success Criteria. Items 10-11 are quality-of-life for daily use. Items 12+ are post-MVP and intentionally under-specified.

1. **Project scaffold.** `npm create tauri-app@latest hearth -- --template react-ts --manager pnpm`. Pin Tauri 2.x. Add `tauri-plugin-sql`, `@tauri-apps/plugin-sql`, `drizzle-kit` (for schema authoring, not runtime), `uuid` (UUIDv7 generator), `zod`, `@tanstack/react-query`, `dnd-kit` (layout drag-and-drop). No `better-sqlite3` directly — see Data Layer Decisions.
2. **SQLite + SQLCipher + event log.** Single-file DB at `~/Library/Application Support/Hearth/hearth.db`. Schema v1 includes `domains`, `layouts`, `blocks`, `records`, `pins`, `proposals`, `event_log`, plus `PRAGMA user_version` for migrations. SQLCipher key derived from macOS keychain (`security find-generic-password`). Shared Rust crate `hearth-core` exposing `applyMutation()` (single SQLite transaction wrapping event_log insert + table mutation).
3. **Layout-store API (Rust).** TypeScript types for `Domain`, `Layout`, `Block`, `Pin`, `Proposal`. CRUD via Tauri commands (`invoke('layout.update_block', ...)`). All writes route through `hearth-core::applyMutation()`. Read APIs query tables directly.
4. **MCP server (`hearth-mcp` binary).** Standalone Rust binary (separate crate in same Cargo workspace). stdio JSON-RPC. Five tools (see MCP Transport section). Spawned by Hermes via MCP config; the Tauri app does not embed or manage it. Hermes stays the chat host; Hearth stays the data + UI host.
5. **Default layouts (seed on first launch).** Seed `finance`, `health`, `fitness`, `tasks`, `email`, `habits` domains. Each gets one v1 block: `table` (finance), `counter` (health, fitness, habits), `list` (tasks, email). See step 8 for block-type definitions.
6. **UI: layout editor.** Sidebar = domain list. Main = layout canvas with drag-add block button, drag-to-reorder, pin toggle per block. Click block → expands to show data + edit affordances. Built with dnd-kit. v1 deliberately not WYSIWYG-rich; this is a working shell, not a Notion-clone.
7. **UI: chat panel — DEFERRED.** No chat panel inside Hearth for v1. The user talks to Hermes in their existing chat surface (Hermes GUI, Claude Code, Codex); Hermes calls MCP tools; Hearth renders the resulting data/layout changes. If the user later wants a chat panel inside Hearth, scope it as a separate project — chat UI is 2-3 weeks of work (streaming, markdown, tool-call display, attachments, cancel, multi-turn context), not "simple".
8. **Block renderers (v1 set).** Five types ship in v1:
   - `table` — sortable, paginated rows with column config; finance domain.
   - `counter` — single value with sparkline (last 30 entries); health, fitness, habits.
   - `list` — title + optional body + checkbox; tasks, email (read-only stub).
   - `note` — single rich-text field (markdown); spare slot for any domain.
   - `chart` — bar/line over `records` data; available but no domain seeds it in v1.
9. **Agent proposal flow.** `hearth-mcp` writes a `proposals` row on `propose_block`. Tauri app polls `proposals` for `status = 'proposed'` rows; renders a banner per affected domain with preview + accept/reject buttons. Accept converts proposal to a `blocks` row (block_id preserved). Reject flips status. Auto-expire after 7 days flips status. All proposal actions route through `applyMutation()` so they're in the event_log.
10. **Backup/restore.** A "Backup now" button in Settings produces a `.tar.gz` archive containing `hearth.db` AND `key.txt` (the SQLCipher key in hex). User picks a destination path via Finder dialog. No iCloud, no cloud, no auto. Restore flow on the same Mac: user drops the `.tar.gz` back, Hearth detects the archive in Settings → Restore, prompts for confirmation, extracts to `~/Library/Application Support/Hearth/`, imports `key.txt` into keychain via `security add-generic-password` (overwrites if exists), opens DB with the imported key. **Round-trip integrity is required.** **The env var `HEARTH_DB_PATH` lets power users point Hearth at an alternate DB location (e.g. for testing); the UI also exposes this in Settings → Database path.** UI prominently documents: **"Losing the key = losing the data. Keep both safe."**
11. **Timezone + currency policy.** All timestamps stored as ISO 8601 UTC with IANA timezone string in a sibling column for display. Currency as ISO 4217 code (`RUB`, `USD`, `EUR`, …) in a sibling column. Display layer formats per user preference; storage is unambiguous.
