# Adversarial Review: cortex standalone (TanStack Start)

Док: effgenij-cortex-design-20260908-180300.md (Builder, DRAFT, 2026-09-08)
Ревьюер: adversarial, свежий контекст. Проверяемые факты платформы (@modelcontextprotocol/sdk stdio+HTTP, TanStack Start server functions/SSR, Drizzle+SQLite, tRPC end-to-end, docker compose) — подтверждены как достоверные.

**Общая оценка: 7.5 / 10**

Док зрелый: явные premises с ревизиями, отклонённые альтернативы с effort/risk, open questions с дефолтами, проверяемые success criteria. Главные дыры — транспортно-процессная модель MCP (внутреннее противоречие) и безопасность MCP HTTP-эндпоинта при VPS-каноничном деплое.

---

## 1. Completeness — FAIL (2 конкретные дыры)

**1.1. Не описана безопасность MCP HTTP-эндпоинта.**
В архитектуре MCP-сервер имеет HTTP-транспорт, а open question 1 предполагает каноническую копию на VPS — то есть MCP HTTP-эндпоинт будет торчать в сеть (или хотя бы в VPS-порт). В доке указана аутентификация только для UI («один пользователь, пароль/токен»). Про то, как HTTP MCP-инструменты cortex.* защищены (токен? тот же пароль? mTLS? bind на localhost + reverse proxy?), — ни слова. Открытый MCP-эндпоинт = любой, кто достучался, пишет в заметки/задачи/привычки. Для OSS-проекта, который другие будут поднимать на VPS, это первый вопрос в issues.
*Fix:* добавить в раздел «Аутентификация v1» пункт: MCP HTTP-транспорт защищён bearer-токеном (переменная окружения `CORTEX_MCP_TOKEN`), генерируемым при первом запуске; stdio — аутентификации не требует (локальный процесс). Внести в success criteria: «MCP HTTP без токена отвечает 401».

**1.2. Нет ни бэкапов, ни экспорта данных.**
Приложение — единственная каноническая база личных данных (notes/projects/todo/habits/calendar) в SQLite-файле. В доке: volume переживает пересоздание контейнера (критерий 5) — это не бэкап. litestream упоминается только как вариант open question 1. Экспорт данных (JSON/Markdown) не упомянут вообще — а для personal-data OSS это и защита от lock-in, и требование комьюнити («как мне уйти с вашего приложения?»).
*Fix:* добавить в v1: (а) документированный бэкап SQLite-файла из volume (litestream или cron `sqlite3 .backup`), (б) команду экспорта всего домена в JSON/Markdown — можно даже в этапе 2, но она должна быть в плане явно.

**1.3 (минор). TLS для VPS-сценария не упомянут.**
Если web на VPS доступен «по сети» — пароль/токен по голому HTTP. Нужна одна строка: reverse proxy (Caddy/Traefik) с TLS в рекомендованном деплое или в docker-compose примере.

## 2. Consistency — FAIL (одно реальное противоречие)

**2.1. «MCP в том же процессе» противоречит stdio-транспорту и Docker-деплою.**
Approach A: «MCP в том же процессе». Но stdio-транспорт работает так: агент-клиент (Hermes) сам спавнит процесс MCP-сервера — физически это отдельный процесс от web-сервера. А если приложение в Docker (главный сценарий распространения, `docker compose up`), то спавн stdio-процесса Hermes'ом на хосте вообще не имеет доступа ни к процессу в контейнере, ни к SQLite-файлу внутри volume. Формулировка «stdio на той же машине или HTTP на VPS» частично признаёт проблему, но не разрешает её: «на той же машине» при Docker-деплое не работает.
*Fix:* зафиксировать транспортную матрицу: (а) HTTP MCP — в процессе web-приложения, основной путь для Docker/VPS; (б) stdio — отдельная точка входа пакета `packages/mcp` для bare-metal установки, разделяющая тот же SQLite-файл (WAL + busy_timeout); (в) для Docker+локальный Hermes — только HTTP (порт контейнера). Убрать «в том же процессе» или уточнить «в процессе web для HTTP-транспорта».

**2.2 (минор). «React Native переиспользует core» — преувеличение.**
`packages/core` содержит Drizzle-схемы (серверные) и zod. RN-клиент переиспользует zod-схемы и типы, но не Drizzle/бизнес-логику, привязанную к серверу. Переформулировать: «переиспользует типы и zod-схемы».

## 3. Clarity — PASS (с двумя рекомендациями)

Структура чистая: premises нумерованы и трассируются в решения, open questions имеют дефолты, критерии проверяемы. Замечания не блокирующие:

**3.1.** Фраза «одна каноническая копия на VPS (web достукивается по сети)» двусмысленна: если читать как «удалённые машины достукиваются к SQLite-файлу по сети» — это известный опасный путь (SQLite не рассчитан на сетевые ФС). Судя по контексту, имеется в виду «пользователи открывают web-UI VPS через браузер», но стоит сказать прямо: «файл БД трогает только один процесс на VPS; другие машины работают через web-UI, не через БД».

**3.2.** «События изменений — для будущих клиентов» — механизм не назван (in-process event bus? SSE? Outbox?). Для v1 достаточно одной строки-заглушки, но сейчас это звучит как бесплатное обещание.

## 4. Scope — PASS (с одной рекомендацией)

Дисциплина хорошая: вьюхи срезаны до списков/таблиц, RRULE отложен (с оговоркой «хранить поля под повторения» — правильная цена опции), mail и отдельные приложения вынесены. Замечание:

**4.1 (рекомендация). Rich-text редактор — кандидат на срез из v1.**
Open question 2 дефолтит к TipTap (ProseMirror) с пометкой «проверить вес». TipTap — это самый тяжёлый UI-компонент во всём v1 (интеграция с формами, сериализация, миграция контента). Для списков/таблиц как единственных вьюх v1 markdown-textarea + превью закрывает критерий 2 полностью и экономит заметную часть T3. Совет: дефолт поменять на markdown-only, TipTap — этап 2, когда появятся богатые вьюхи.

**4.2 (минор).** Критерий 6 («новый модуль без изменения ядра») — хорошая расширяемость, но проверяется фактом только если migrations наружу тоже не требуют изменения ядра; сформулировать «схема + миграция + роутер + MCP-группа, ядро не меняется».

## 5. Feasibility — PASS (стек подтверждён, один риск деплоя)

Все платформенные допущения точны: @modelcontextprotocol/sdk действительно даёт stdio+HTTP; TanStack Start — server functions, SSR; Drizzle поддерживает SQLite (better-sqlite3/libsql) и миграции; tRPC типобезопасен end-to-end; docker compose — стандарт распространения. Self-осознанный риск («фреймворк моложе Next.js») адекватен.

**5.1 (покрывается 2.1).** Единственный реальный риск feasibility — combo Docker + stdio MCP (см. 2.1): процесс в контейнере нельзя заспавнить stdio-клиентом на хосте, и наоброт. Это не «невозможно», это требует явной транспортной матрицы из фикса 2.1 — без неё первый сторонний пользователь на Docker упрётся в «как подключить Hermes?».

**5.2 (минор).** WAL при двух процессах (web + stdio MCP) на одном файле — работает, но добавить `busy_timeout` (и сказать об этом в доке), иначе при конкурентной записи будут SQLITE_BUSY всплывать как ошибки UI.
