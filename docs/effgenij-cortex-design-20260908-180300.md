## Problem Statement

Нужна единая self-hosted база личных данных (notes, projects, todo, habits, calendar), видимая перед глазами и доступная агенту (Hermes, позже openclaw). Готовые приложения (Notion, AFFiNE, AppFlowy, routine, amie, sunsama) проприетарны или берут платную подписку на ИИ; у пользователя уже есть Hermes — он хочет использовать его ИИ в своих приложениях без доплаты. Решение: собственное self-hosted OSS-приложение с MCP-интеграцией Hermes, рассчитанное в первую очередь на личное использование, но пригодное для установки и развития другими.

## What Makes This Cool

- **Свой ИИ, ноль подписок:** все агентные функции делает Hermes, которого пользователь уже имеет и оплачивает; приложение само по себе работает без ИИ-ключей.
- **Агент и данные — соседи:** Hermes пишет/читает те же таблицы, что и UI, через MCP-инструменты — «добавь задачу на завтра» из чата появляется в интерфейсе.
- **МодульныйOSS:** не «плагин для одной платформы», а самостоятельное приложение, которое любой может поднять командой docker compose up и подключить своего агента.

## Constraints

- **Full TypeScript.** Никакого Python/FastAPI в ядре (решение пользователя, D-ревизия P1). MCP-сервер — `@modelcontextprotocol/sdk` (официальный TS SDK).
- Self-hosted, open source, личное использование first; standalone-режим без Hermes (свой LLM-ключ) — этап 2+.
- v1 = web self-hosted (Docker). Telegram/iOS/Android/desktop — этапы после стабилизации web.
- Mail НЕ в v1 (IMAP/SMTP — тяжёлая подсистема): этап 2, скорее интеграция готового webmail, чем своя реализация.
- Отдельные приложения (финансы, здоровье, новости, обучение) — после стабилизации базового приложения, поверх общих данных и аутентификации.
- Продуктовые ориентиры UX: Notion, AFFiNE, routine, amie, sunsama.

## Premises

P1. Пивот принят: плагин Hermes → standalone self-hosted OSS web-приложение. Плагин-док архивируется; переносится идея SDK-независимого ядра (схемы, REST/tRPC, MCP-инструменты), код не переносится (его не было). *(D1, ревизия: full TS)*
P2. v1-домены: notes, projects, todo, habits, calendar. Mail — этап 2. *(D1 + D3)*
P3. Вьюхи v1 — только списки/таблицы (без канбана/календаря); богатые вьюхи — этап 2. *(D3 — выбран вариант C)*
P4. Интеграция Hermes — MCP-сервер поверх доменного ядра. Standalone-ИИ (свой ключ) — этап 2+. *(D1)*
P5. Отдельные приложения (финансы, здоровье, новости, обучение) — не в v1. *(D1)*
P6. Клиенты beyond web — после стабилизации web. *(D1)*
P7. OSS-обвязка (LICENSE, README, docker-compose) — в v1; коммьюнити-работа не блокер. *(D1)*
P8. Стек: TanStack Start monorepo (pnpm workspaces), tRPC, Drizzle ORM, SQLite. Один Docker-образ. *(D2 — вариант A, фреймворк заменён пользователем на TanStack Start)*

## Approaches Considered

### Approach A: TanStack Start full-stack monorepo (выбрано)
apps/web (TanStack Start: UI + API/server functions + tRPC + Drizzle + SQLite), packages/mcp (MCP-сервер для Hermes), packages/core (доменные схемы и логика). Один Docker-образ, один язык.
Effort: M · Risk: Low-Med
Pros: один Docker-образ — сторонние пользователи стартуют `docker compose up`; типы от схемы БД до UI без дублирования; MCP в том же процессе (HTTP-транспорт); React-экосистема общая с будущими мобильными клиентами (React Native переиспользует типы и zod-схемы из core).
Cons: фреймворк моложе Next.js — реже чинишь чужие проблемы, чаще читаешь changelog; server functions специфичны для Start — при переезде на другой бэкенд API-слой переписывается.

### Approach B: Fastify/NestJS бэкенд-сервис + React SPA (Vite) (отклонено)
Effort: M-L · Risk: Med
Pros: чёткая граница REST — будущим Telegram/iOS/desktop клиентам проще; сервисы независимы.
Cons: два деплоя в docker-compose, дублирование типов/валидации, boilerplate аутентификации — для личного self-hosted масштаба лишнее.

### Approach C: FastAPI сервис + TS фронт (отклонено пользователем)
Effort: S-M · Risk: Low
Pros: минимальные изменения относительно плагин-дока.
Cons: два языка/две экосистемы — против требования пользователя «полностью TS».

## Recommended Approach

**A — TanStack Start monorepo.** Один язык, один деплой, максимум переиспользования типов; MCP-пакет — та же точка расширения для openclaw и любых агентов.

Архитектура:
```
cortex/
├── apps/web/                  # TanStack Start: UI + server functions + tRPC
│   ├── src/routes/            # /dashboard /notes /projects /todo /habits /calendar
│   ├── src/modules/           # UI-модули доменов
│   └── src/server/            # tRPC-роутеры, Drizzle-клиент
├── packages/core/             # домен: схемы Drizzle, zod-валидация, бизнес-логика (SDK-независимо)
├── packages/mcp/              # MCP-сервер: инструменты cortex.* поверх core (stdio + HTTP)
├── docker/ (Dockerfile, docker-compose.yml)
├── LICENSE, README.md
```
- БД: SQLite (файл в volume), Drizzle-миграции; WAL + `busy_timeout` (при двух процессах — web и stdio MCP на одном файле — без него конкурентная запись даёт SQLITE_BUSY в UI).
- **Транспортная матрица MCP (фикс ревью 2.1):** (а) HTTP MCP — внутри процесса web-приложения, основной путь для Docker/VPS-деплоя; (б) stdio — отдельная точка входа `packages/mcp` для bare-metal установки на той же машине, тот же SQLite-файл; (в) Docker + локальный Hermes — только HTTP (порт контейнера). «MCP в том же процессе» верно только для HTTP-транспорта.
- **Безопасность MCP HTTP (фикс ревью 1.1):** bearer-токен из `CORTEX_MCP_TOKEN` (генерируется при первом запуске, выводится в лог); без токена — 401. Stdio — без аутентификации (локальный процесс). Рекомендованный VPS-деплой — reverse proxy (Caddy/Traefik) с TLS перед web-UI и MCP HTTP.
- **Бэкап и экспорт (фикс ревью 1.2):** документированный бэкап SQLite из volume (cron `sqlite3 .backup` или litestream — инструкция в README); команда экспорта домена в JSON/Markdown (lock-in-защита, требование OSS-комьюнити) — в v1 минимально JSON, Markdown — этап 2.
- Домены v1: notes (JSON-документы), projects (группировка задач/заметок), todo (строгая схема), habits (строгая схема, стрики-агрегаты), calendar (события). Вьюхи v1: списки/таблицы.
- Редактор заметок v1: markdown textarea + превью (TipTap — этап 2, richest-вьюхи). *(дефолт OQ2 изменён по рекомендации ревью)*
- MCP-инструменты v1: cortex.tasks.* (CRUD), cortex.habits.* (log/checkin/list), cortex.notes.* (search/create/append), cortex.projects.*, cortex.calendar.*; события изменений — in-process event bus как заготовка (для SSE/будущих клиентов), механизм детализируется в этапе 2.
- Интеграция Hermes: подключение MCP-сервера в конфиге Hermes (stdio на bare-metal, HTTP на VPS/Docker). Openclaw/другие агенты — тот же MCP.
- Аутентификация v1: один пользователь (пароль/токен), без мульти-тенантности.
- Синхронизация: файл БД трогает только один процесс на машине-каноне; другие машины работают через web-UI в браузере, не через БД напрямую (SQLite по сетевым ФС — запрещённая топология).

## Success Criteria

MVP «готов», когда:
1. `docker compose up` поднимает приложение; `http://host:port` открывает dashboard с 5 разделами.
2. Все 5 доменов: создать/открыть/отредактировать запись руками в web-UI.
3. Hermes подключён через MCP и: «добавь задачу X на завтра» → задача видна в /todo без перезагрузки (polling/рефetch); «отметь привычку Y» → стрик обновился; «найди заметку про Z» → результат из поиска.
4. MCP HTTP без токена отвечает 401; UI защищён паролем.
5. Дерево проектов слева, активный домен в центре; тёмная/светлая тема не приоритет.
6. Docker volume переживает пересоздание контейнера — данные на месте; бэкап-инструкция из README восстанавливает базу из копии; экспорт домена в JSON работает.
7. Новый модуль (например, workouts) добавляется схемой + миграцией + роутером + MCP-группой без изменения ядра — расширяемость проверена фактом.
8. README + LICENSE + docker-compose: посторонний человек может запустить без вопросов автору.

## What I noticed about how you think

- «Я не хочу платить дополнительно, у меня есть hermes» — ты формулируешь ценность не как фичу, а как экономику: свой агент уже куплен, приложение должно просто пустить его к данным.
- Четвёртая итерация архитектуры, и каждая сокращает дистанцию до первого работающего артефакта: Tauri → web → плагин → самостоятельное приложение. Пивот к standalone — не откат к Hearth: Hearth был «приложение + встроенный чат», это — «приложение + MCP-мост для любых агентов», и каркас уже продуман в плагин-доке.
- «Пусть так же будут рассчитаны что кто-то захочет их ставить» — OSS как цель с самого начала меняет дисциплину: Docker, README, лицензия — в v1, а не «когда-нибудь потом».
- Ты сам срезал вьюхи (выбрал вариант C) вместо того, чтобы защищать полный UX — скоуп-дисциплина, которой не хватало в июне.
