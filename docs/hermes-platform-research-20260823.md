# Исследование: личный набор продуктов внутри Hermes Desktop

**Дата:** 2026-08-23 · **Профиль:** default · **Метод:** первоисточники — локальное дерево `~/.hermes/hermes-agent` (исходники + `website/docs/`, те же страницы, что на hermes-agent.nousresearch.com), репозитории NousResearch на GitHub, инвентарь локальных скиллов `~/.hermes/skills/`.

**Вопрос:** как реализовать 9 продуктов (заметки, задачи+привычки, финансы, здоровье, питание, лента, английский, программирование, видеокурсы) — одно приложение, несколько плагинов или один плагин? Без отдельного сайта; позже — веб.

---

## TL;DR — рекомендация

> **Актуально:** см. дополнение ниже — требование визуализации/дашбордов меняет п.1–2 на «один воркспейс-плагин с модулями». Пп. 3–4 остаются в силе.

1. **Не сайт и не 9 отдельных продуктов.** Делать **4 гибридных плагина по доменам данных** + финансы тонким слоем поверх уже работающего скилла ZenMoney. Один домен = одно хранилище = одна папка-плагин.
2. Каждый плагин — **гибрид «одна папка»**: агентная половина (`plugin.yaml`, инструменты, скиллы) + десктопная половина (`desktop/plugin.js`: страница в сайдбаре, панели, карточки в чате) + Python-бэкенд (`dashboard/plugin_api.py`). Это документированная схема, не хак.
3. **Веб потом почти бесплатно:** единственное, что разделяют десктопный и веб-дашборд SDK — это бэкенд `plugin_api.py` (`/api/plugins/<id>/`). Строишь логику там → веб-версия позже добавляется вкладкой дашборда поверх тех же маршрутов.
4. **Интеллект и склейка доменов — не в коде плагинов, а в агенте:** скиллы + cron + память. Плагины дают данные и UI; кросс-доменные сценарии («из видео в ленте собери рецепт → добавь в меню недели») делает сам Hermes через инструменты. Прямые вызовы между бэкендами разных плагинов платформой не поощряются (`ctx.rest` жёстко замкнут на своё пространство имён).

## ⚠️ ДОПОЛНЕНИЕ (2026-08-23, вечером): главное требование — визуализация

Уточнение пользователя: весь этот функционал Hermes и так умеет делать в чате — неудобно именно то, что нет **визуализации перед глазами**. Нужны дашборды: заметки, inbox, прогресс обучения (отметки «где прошёл»), здоровье, тренировки, питание, рецепты, деньги, задачи, привычки. Ориентир — Notion: база данных как ядро, поверх неё любые вьюхи (дашборды, заметки, to-do).

### Что это меняет в рекомендации

**Было:** 4 гибридных плагина по доменам. **Стало: один воркспейс-плагин с модулями внутри.**

Техническое обоснование пересмотра:

1. **Хоум-дашборд кросс-доменен по определению**, а `ctx.rest` плагина жёстко замкнут на собственный неймспейс `/api/plugins/<свой-id>/` (traversal отклоняется намеренно) — страница одного плагина не может агрегировать данные четырёх других иначе как через агента. Смешанный виджет-грид («задачи + пульс финансов + стрики привычек + счётчик inbox») требует общего хранилища → одна папка, один SQLite.
2. **Нотион-модель = одна примитивная сущность + много вьюх.** Это про единое пространство данных со связями (задача ↔ рецепт ↔ тренировка ↔ заметка), а не про отдельные приложения.
3. Операционно проще: один enable-переключатель, один data-dir, один бэкенд, который потом же обслужит и веб.

### Архитектура воркспейс-плагина

```
~/.hermes/plugins/workspace/
├── plugin.yaml            # агентные инструменты всех модулей
├── __init__.py            # register(ctx)
├── skills/…               # скиллы (брифинг, меню недели, план тренировок…)
├── dashboard/
│   ├── manifest.json      # {"name":"workspace","api":"plugin_api.py"}
│   └── plugin_api.py      # FastAPI: /bases/<имя>/… — CRUD + запросы над SQLite
└── desktop/
    └── plugin.js          # шелл: страницы разделов + хоум-дашборд + виджеты
```

- **Ядро — «базы»**: типизированные SQLite-таблицы (tasks, habits, notes, recipes, workouts, measurements, feed_items, lessons, transactions_cache) + связи между ними.
- **Модули доменов** регистрируют в общий шелл: свои базы, вьюхи, виджеты для хоума, агентные инструменты. Новый домен = новый модуль, не новое приложение.
- **Набор вьюх (не бесконечный, фиксированный)**: список/таблица, канбан, календарь, галерея (рецепты), stat-карточки + спарклайн, прогресс-бары (обучение). Дженерик-движок «любая БД × любая вьюха» уровня Notion — не цель; фиксированный набор вьюх над типизированными таблицами покрывает все 9 продуктов и остаётся подъёмным.

### Три поверхности визуализации

1. **Разделы в сайдбаре** (`ROUTES_AREA` + `SIDEBAR_NAV_AREA`): Notes / Tasks / Habits / Money / Body / Feed / Learning — каждая страница рендерит вьюхи над базами.
2. **Хоум-дашборд**: конфигурируемая сетка виджетов из всех баз сразу (главный экран, ради него всё затевалось).
3. **Виджеты в чате**: `::preview{file="…"}` HTML-виджеты (в sandbox-iframe разрешены любые скрипты — тяжёлые графики можно вынести сюда) и транскрипт-директивы вроде `::task{id}`; двусторонняя связь через `window.hermes.send()`.

### Жёсткое ограничение по графикам

Disk-плагин импортирует только `@hermes/plugin-sdk`, `react`, `react/jsx-runtime` — **никаких chart-библиотек** (recharts и т.п. не зарезолвятся). Графики на страницах = собственные SVG-компоненты (спарклайны, бары, линии — это просто) или `<canvas>` (SDK прямо предусматривает canvas-панели с ResizeObserver и чтением `--ui-*` переменных). Для сложных чартов — HTML-файл с встроенной библиотекой внутри `::preview`.

### Что не меняется

Интеллект — у агента (скиллы + cron + память); финансы — тонкий слой над ZenMoney-скиллом без своего синка; веб потом — те же маршруты `plugin_api.py` + вкладки дашборда.

**Стартовая петля:** каркас шелла (сайдбар + роутер + хоум-грид) → база «Задачи» + канбан → хоум с 3–4 виджетами (задачи на сегодня, стрики, inbox-счётчик, фин-снимок). Дальше модули по одному.

### Отдельные агенты на тему: Bot Mode

Источник: `website/docs/user-guide/bot-mode.md`.

- **Bot Mode** встроен в десктоп-приложение, включён по умолчанию: вкладка **Bots** рядом с Sessions. **Бот = профиль Hermes** (`~/.hermes/profiles/<name>/`) — изолированные конфиг, память, скиллы, креденшалы и история чата. Никакой новой сущности и демонов.
- Создание: **New Agent** → имя/роль/описание; в Advanced — клон существующего профиля, пин своей модели/провайдера, собственный SOUL.md (персона и постоянные инструкции), точечное включение скиллов/тулсетов/MCP. У каждого бота — вечный канонический Bot Chat.
- **Routines** — обычные cron-задания, приписанные боту (`[bot:<имя>] …`, видны в `hermes cron list`); результат падает в чат того самого бота.
- **Взаимодействие:** @mentions из любого чата, прямые DM между ботами (`message_agent`), групповые комнаты 2–6 ботов (до 3 серийных раундов на сообщение, капа 10 сообщений, эскалация к человеку бейджем «needs you»). CLI-эквивалент: `hermes -p <bot> chat`.
- Отличать от `delegate_task`-сабагентов: те — одноразовые воркеры внутри чужого разговора без собственной памяти; бот — постоянный специалист со своим чатом, рутинами и накопленным контекстом.

Распределение ролей в архитектуре: **плагин workspace владеет данными и визуализацией, боты — персоны и исполнители поверх общих баз.** Инструменты плагина регистрируются агентно и доступны любому профилю, которому включён этот тулсет → финансовый бот пишет транзакции в ту же SQLite, из которой читает дашборд, — независимо от того, кто писал. Ростер под продукты: 💰 Финансы (скилл zenmoney-finance-analysis), 🏋 Тело (тренировки+питание), 📥 Лента (рутинные поллинги), 🎓 Коуч (обучение), заметки/задачи остаются у основного агента. Префикс `[bot:<name>]` в cron держит рутины разных ботов раздельными.

### Три машины пользователя: синхронизация

Источник: `website/docs/user-guide/multi-connection-desktop.md`, `bot-mode.md` («Create on», peers), `desktop-plugin-sdk.md` (локальность десктоп-половины).

Топология: рабочий ПК (Windows) + домашний Mac + VPS с Hermes (веб, 24/7).

**Модель платформы:** агент (= профиль), его сессии, память, cron и файлы живут на **машине-гейтвее**, а не в приложении. Десктоп — окно на зарегистрированные гейтвеи: Settings → Gateways добавляет подключения, ростер ботов показывает объединённый список всех машин (`host.agents()`), открытие агента дial'ит его собственный гейтвей. Сессии/cron/память всегда скоупятся к активной паре `(гейтвей, профиль)`.

Следствия для пользователя:

1. **Боты создаются один раз на VPS** (в диалоге New Agent есть пикер «Create on») → они видны из Mac, из Windows и из веб-дашборда без какой-либо синхронизации — единственная каноническая копия.
2. **Scheduled jobs по определению крутятся там, где живёт бот-владелец** → создав ботов на VPS, рутины становятся always-on автоматически (cron скоупится к своему гейтвею).
3. **Общая память:** переписка с VPS-агентами копится в памяти/сессиях на VPS независимо от того, с какого компьютера печатаешь. Локальные профили Mac/Windows остаются для работы с локальными файлами (VPS-агент физически не видит диски компьютеров); результаты передаются VPS-боту через @mention или `hermes peer` (кросс-машинные DM, `message_agent(target="vps/финансы", …)`).
4. **Плагин workspace:** Python-бэкенд + SQLite включаются только в конфиге VPS-профиля → одна база навсегда. Десктопная половина (`desktop/plugin.js`) ставится файлом на оба компьютера (важно: скан десктоп-плагинов локален по машине, против удалённого бэкенда работает только локально установленный UI) — `ctx.rest` достукивается до `/api/plugins/workspace/` того бэкенда, к которому присоединена сессия, т.е. к VPS. Веб-версия на VPS читает те же маршруты. Итог: данные в одном экземпляре, UI везде.
5. Прочее: «Update all instances» обновляет флот параллельно; токены подключений шифруются в OS-keychain; `hermes profile export/import` переносит профиль между машинами при переезде. SQLite не синхронизируют построчно и не гоняют через git — вместо этого одна каноническая копия на VPS (+ бэкап/Litestream при желании).

## 1. Что позволяет платформа (факты с источниками)

### 1.1 Три независимые системы плагинов

| Система | Что расширяет | Технология |
|---|---|---|
| Agent-плагин | инструменты, хуки, slash/CLI-команды, скиллы агента | Python, `register(ctx)` |
| Desktop-плагин | панели, страницы, сайдбар, статусбар, палитра ⌘K, кейбинды, темы, композер, карточки в транскрипте | один ESM-файл `@hermes/plugin-sdk` |
| Dashboard-плагин (веб) | вкладки, слоты шелла, темы веб-дашборда | `manifest.json` + JS-бандл |

Источник: `website/docs/developer-guide/desktop-plugin-sdk.md` (стр. 23–33): «The three do not share code, APIs, or delivery. Only the backend `plugin_api.py` namespace (`/api/plugins/<id>`) is shared between the desktop and dashboard SDKs». Аналогичная плашка в `website/docs/user-guide/features/extending-the-dashboard.md`.

### 1.2 Agent-плагин (Python)

Источник: `website/docs/developer-guide/plugins/index.md`.

- Каркас: `~/.hermes/plugins/<id>/` c `plugin.yaml` + `__init__.py` (`register(ctx)`), опц. `schemas.py`/`tools.py`; проектные плагины `.hermes/plugins/` выключены по умолчанию.
- Регистрация: `ctx.register_tool/register_hook/register_command (slash)/register_cli_command/register_skill` (скиллы неймспейсятся `plugin:skill`); 26 жизненных хуков (`VALID_HOOKS`).
- **Хранилище:** `plugins.plugin_storage.plugin_data_dir("id")` → `<HERMES_HOME>/plugin-data/<id>/`; `plugin_db("id")` → SQLite (WAL, thread-friendly). Правило: состояние **никогда** не хранить в папке плагина (install-tree, умрёт при `update`) — только в data-dir. Плюс `ctx.state` (профиль-скоуп, атомарно, ≤10 МиБ) и `ctx.get_config/set_config` (настройки под `plugins.entries.<id>.settings`, декларируются `config_schema` в манифесте v2). «Neither API exposes another plugin's namespace» — хранилища изолированы по плагинам.
- **LLM из плагина:** `ctx.llm.complete(...)` / `ctx.llm.complete_structured(...)` — заем модели пользователя под одну задачу (парсинг рецептов, оценка уровня английского). Опционально capability `llm.model_override`.
- Связи между плагинами: `requires_plugins` в манифесте v2 — **advisory**, влияет только на порядок загрузки (топологическая сортировка); проверка в рантайме `ctx.has_plugin()`. Общего API доступа к данным чужого плагина нет.
- `ctx.inject_message()` — воткнуть сообщение в разговор CLI/гейтвея (будильники из фоновых задач).
- `requires_env` — интерактивный промпт ключей при установке; установка проходит статический security-скан; плагины opt-in через `plugins.enabled`.

### 1.3 Desktop-плагин (UI приложения)

Источник: `website/docs/developer-guide/desktop-plugin-sdk.md`.

- Установка: `$HERMES_HOME/desktop-plugins/<id>/plugin.js`, папка = id. Загрузка за секунды, **hot-reload каждого сохранения**, без сборки. Только импорты `@hermes/plugin-sdk`, `react`, `react/jsx-runtime`; JSX-синтаксис запрещён — писать `jsx()/jsxs()`.
- Поверхности (contribution areas): `panes` (плейсмент left/right/top/bottom/main + dock), `routes` (полная страница), `sidebar_nav`, `statusbar.left/right`, `titlebar`, `palette` (⌘K), `keybinds`, `themes`, `composer.*`, **`TRANSCRIPT_DIRECTIVE_AREA`** — агент рисует твой React-компонент прямо в сообщении строкой вида `::task{id="42"}`.
- Виджеты в чате двусторонние: `::preview{file=…}` рендерит HTML живьём (sandbox-iframe), а `window.hermes.send('…')` / `data-hermes-send="…"` шлёт промпт агенту скрытым ходом (≤500 симв., троттлинг 1/сек).
- Доступ к данным: `host.request(method, params)` — тот же JSON-RPC, что у самого приложения (сессии, конфиг, скиллы, cron, kanban); `host.onEvent` — поток событий гейтвея; `ctx.rest/ctx.socket` — **только собственное** пространство `/api/plugins/<id>/` (traversal отклоняется — чужой бэкенд из UI не вызвать); `ctx.storage` — персист под `hermes.plugin.<id>.*`.
- ОС-двери: `ctx.os.notify` — нативное уведомление (срабатывает, когда пользователь вне приложения — готовый механизм напоминаний), `openExternal`, `revealPath`, `writeClipboard`.
- UI-кит приложения (Button, Tabs, Dialog, ScrollArea…) + theme-переменные `var(--ui-*)` — плагин выглядит нативно и переживает смену тем.
- Важно: скан десктопных плагинов **локален по машине** — против удалённого бэкенда работает только то, что установлено локально (актуально для будущего веба/удалённого гейтвея).

### 1.4 Гибрид: одна папка — обе половины

Источник: `website/docs/developer-guide/desktop-plugin-sdk.md`, раздел «One package, both SDKs».

```
~/.hermes/plugins/<id>/
├── plugin.yaml            # агентная половина: tools/hooks/commands
├── __init__.py            # register(ctx)
├── skills/…               # скиллы плагина
├── dashboard/
│   ├── manifest.json      # {"name":"<id>", "api":"plugin_api.py"}
│   └── plugin_api.py      # FastAPI router → /api/plugins/<id>/
└── desktop/
    └── plugin.js          # десктопная половина: страницы, панели, ctx.rest
```

Один каталог = установка/удаление одной операцией. Два независимых выключателя (Settings → Plugins для UI-половины; `plugins.enabled` в config.yaml для Python-половины — security boundary GHSA-mcfc-hp25-cjv7), оба по умолчанию **off**. Десктопная половина деградирует мягко, когда бэкенд выключен. Дистрибуция — git-репо или deep-link `hermes://plugin/install?repo=owner/repo&enable=1`.

### 1.5 Уже встроенные механизмы, которые заменяют половину кода

- **Cron** (`website/docs/user-guide/features/cron.md`, 993 строки): расписания любого вида; на задачу — свои скиллы, модель, reasoning-effort, workdir проекта; пре-скрипт сбора данных; `no_agent=True` (чистый скрипт без LLM); монитор-режим `monitor_url`/`monitor_script` (агент просыпается только при изменении — готовая основа RSS-поллинга); доставка в любой чат/платформу, `[SILENT]` для тихих тиков; `context_from`/`continuity` — цепочки задание→задание.
- **Gateway-платформы** (ядро): Telegram, Email, WhatsApp, Signal, Discord и др. (`gateway/platforms/`: signal, whatsapp_cloud, weixin, qqbot, bluebubbles, webhook, msgraph_webhook…) — входящие письма/сообщения сами приходят агенту.
- **Десктоп-приложение** (`website/docs/user-guide/desktop.md`): Projects, Artifacts (галерея файлов/ссылок из сессий), preview-rail, терминал/ревью-панели, переопределяемые хоткеи, палитра команд.
- **Память и session_search** — кросс-сессионный контекст без своей БД «знаний».

### 1.6 Веб-дашборд («Hermes web ui»)

Источник: `website/docs/user-guide/features/extending-the-dashboard.md` (927 строк).

- Три слоя: YAML-темы в `~/.hermes/dashboard-themes/`; UI-плагины (`manifest.json` + JS-бандл: вкладка, `tab.override`, слоты шелла и страниц); бэкенд-плагины (`plugin_api.py` → `/api/plugins/<name>/`).
- Всё drop-in в рантайме, без клонирования репо и сборки.
- Ключевое для стратегии «сначала десктоп, потом веб»: **backend-неймспейс общий** между десктопным и веб SDK → логика пишется один раз.

### 1.7 Ограничения и подводные камни (честно)

- Изоляция плагинов — только error-isolation; загруженный код имеет полную власть приложения. Capabilities — consent-слой, не песочница.
- Данных чужого плагина из коробки не достать: ни `ctx.state`, ни `config`, ни `ctx.rest` не отдают чужее неймспейс. Кросс-плагиновый обмен = через агента (инструменты/скиллы) или свой HTTP API. Это главный аргумент **против** 9 мелких плагинов со связанными данными.
- `ctx.socket` — no-op на OAuth-remote; нужен polling-fallback.
- `python_dependencies` в манифесте — только декларация, автоустановки нет.

## 4. Архитектура: сколько плагинов и какие

**Не 9.** Данные внутри домов связаны сильнее, чем между домами, а платформа не даёт удобного межплагинового обмена → группируем по хранилищу.

### Плагин A — `life-hub` (заметки + задачи + привычки + финансы-дашборд)
- Хранилище: один SQLite (`plugin_db`) — заметки (markdown), задачи, привычки (стрики), кэш фин-снимков.
- UI: страница `/life` с вкладками (Notes/Tasks/Habits/Money) + `::task{}`-карточки в чате + статусбар-счётчик.
- Агентная часть: инструменты CRUD, скилл «утренний брифинг», cron-напоминания (`ctx.os.notify`), привычки-чекины.
- Финансы: **без собственного синка** — читает ZenMoney через существующий скилл; бюджет-диалоги ведёт агент. Отдельный плагин не оправдан: источник внешний, связей с заметками мало.

### Плагин B — `body` (здоровье + питание)
- Почему вместе: дневной лог общий (сон/вес/тренировки/приёмы пищи/КБЖУ), меню недели зависит от тренировок.
- Агентная часть: парсер рецептов (`ctx.llm.complete_structured` → строгая схема КБЖУ), генератор меню на неделю + prep-лист, планировщик тренировок, статистика. Ингест браслета — отдельный вопрос (см. §6).
- UI: день-лента, календарь тренировок, библиотека рецептов.

### Плагин C — `inbox-feed` (лента)
- Источники: RSS-поллинг (cron `monitor_url`/`monitor_script`), письма (gateway Email/`himalaya`), Telegram (бот/гейтвей), YouTube (`youtube-content`).
- Фильтрация — агент по правилам пользователя; результат — очередь «к просмотру» с аннотациями.
- Отдаёт находки дальше: рецепты → B, курсы/видео → D (через агента, который перекладывает между инструментами плагинов).

### Плагин D — `learning` (английский + программирование + видеокурсы)
- SRS-движок (алгоритм повторений в SQLite), план обучения, журнал сессий с оценкой.
- Конвейер видеокурса: транскрипт → структура курса → «ключевые моменты» с таймкодами → сгенерированная практика → отслеживание выполнения.
- Разговорный английский — вообще без UI: обычный чат с Hermes по скиллу; UI нужна только очередям повторений.

**Правило разреза:** новый продукт = новый плагин только если у него собственное хранилище. Иначе — вкладка/панель внутри существующего.

## 5. Дорожная карта

0. **Каркас и петля разработки** (полдня): `~/.hermes/desktop-plugins/life-hub/plugin.js` со страницей-заглушкой → проверить hot-reload; затем перенести в гибридную папку `~/.hermes/plugins/life-hub/` c `plugin_api.py` и убедиться, что `ctx.rest` достукивается.
1. **A-min: задачи+привычки** — SQLite-стор, CRUD-инструменты, `::task`-карточка, cron-напоминания.
2. **C-min: RSS+YouTube** — cron-мониторинг, фильтр агентом, очередь просмотра.
3. **B: питание** — парсер рецептов, библиотека, меню недели; затем тренировки и ингест браслета.
4. **D: SRS английского**, затем конвейер видеокурсов.
5. **Финансы** — вкладка Money поверх скилла (в любой момент, риск нулевой).
6. **Веб** — добавить `dashboard/manifest.json`-вкладки тем же плагинам; маршруты `/api/plugins/<id>` уже готовы. Дистрибуция — `hermes://` ссылки.
